## CLAUDE.md란?

Claude Code는 세션을 시작할 때 작업 디렉토리를 탐색해 `CLAUDE.md` 파일을 찾고 자동으로 읽는다. 이 파일은 Claude에게 "이 프로젝트에서 어떻게 행동해야 하는가"를 알려주는 지침서다.

코드베이스의 규모가 클수록, 팀 컨벤션(코딩 규칙)이 복잡할수록 CLAUDE.md의 역할이 중요해진다. Claude는 파일을 직접 읽어 언어나 프레임워크의 패턴을 어느 정도 유추할 수 있지만, 다음과 같은 것은 파일만 보고 알기 어렵다.

- 팀이 선호하는 브랜치 전략이나 커밋 메시지 형식
- 특정 라이브러리 대신 자체 유틸리티를 써야 하는 이유
- 테스트를 실행하는 정확한 명령과 플래그
- 배포 전 반드시 통과해야 하는 체크리스트

이런 맥락을 CLAUDE.md에 명시하면 Claude는 매 세션마다 동일한 수준의 이해를 갖고 작업을 시작한다.

### 시스템 프롬프트와의 관계

CLAUDE.md는 사실상 프로젝트 전용 시스템 프롬프트로 동작한다. Claude Code는 이 파일의 내용을 컨텍스트(문맥) 창의 초반부에 주입한다. 따라서 지침이 길고 상세할수록 실제 작업에 쓸 수 있는 컨텍스트가 줄어든다. 시스템 프롬프트 설계의 원칙에 대해서는 [claude/03-시스템-프롬프트-설계.md](../claude/03-시스템-프롬프트-설계.md)를 참조한다.

## 계층 구조

CLAUDE.md는 네 개의 계층으로 동작하며, 계층마다 적용 범위와 관리 주체가 다르다.

### 1. 관리 정책 레벨 (Enterprise)

조직 관리자가 설정하는 최상위 계층이다. 개별 사용자가 덮어쓸 수 없으며, 보안 정책이나 준수해야 할 사내 규정을 배포할 때 사용한다.

저장 위치는 운영 체제별로 다르다.

| OS | 경로 |
|---|---|
| macOS | `/Library/Application Support/ClaudeCode/CLAUDE.md` |
| Linux | `/etc/claude-code/CLAUDE.md` |
| Windows | `C:\Program Files\ClaudeCode\CLAUDE.md` |

### 2. 프로젝트 레벨

가장 자주 사용하는 계층이다. 두 위치 중 하나에 파일을 두면 된다.

```
./CLAUDE.md              # 프로젝트 루트
./.claude/CLAUDE.md      # .claude 디렉토리 안
```

이 파일은 git에 커밋해 팀 전체가 공유한다. 프로젝트의 코딩 스타일, 테스트 방법, 아키텍처 결정 등 팀 전체에 적용할 지침을 담는다.

### 3. 하위 디렉토리 레벨

프로젝트의 하위 디렉토리에 `CLAUDE.md` 파일을 추가로 둘 수 있다. Claude가 해당 디렉토리의 파일을 작업할 때 온디맨드(on-demand)로 로드된다. 대규모 모노레포에서 서비스별로 다른 지침을 적용할 때 유용하다.

### 4. 사용자 레벨

특정 프로젝트가 아닌 사용자 개인에게 항상 적용되는 설정이다.

```
~/.claude/CLAUDE.md
```

자신만의 작업 스타일, 선호하는 출력 형식, 개인적인 워크플로 지침을 저장한다. 팀의 CLAUDE.md와 충돌하면 팀 설정이 우선한다.

### 우선순위

```
관리 정책 > 프로젝트 > 하위 디렉토리 > 사용자
```

하위 계층의 지침이 상위 계층과 충돌하면 상위 계층이 이긴다. 각 계층의 내용은 합산되어 Claude에게 전달되므로, 중복 없이 적절한 계층에 지침을 배치하는 것이 중요하다.

## 효과적인 CLAUDE.md 작성

### 목표 크기

200줄 미만을 목표로 한다. CLAUDE.md는 Claude의 컨텍스트 창을 직접 소비하기 때문에 길수록 실제 작업 공간이 줄어든다. 긴 파일이 필요하다면 아래에서 설명하는 `@문법`을 사용해 외부 파일로 분리한다.

### 포함할 항목

**자주 쓰는 Bash 명령어**: 테스트 실행, 빌드, 린트 등 반복적으로 사용하는 명령을 명시한다. Claude가 추측 없이 올바른 명령을 사용할 수 있다.

**코드 스타일과 컨벤션**: 자동 포매터로 강제되지 않는 팀 고유의 규칙을 적는다. "함수는 명사형이 아닌 동사형으로 시작한다", "에러 처리는 반드시 커스텀 AppError 클래스를 사용한다" 같은 내용이 해당된다.

**아키텍처 결정**: 특정 패턴을 선택한 이유나 피해야 할 접근 방식을 적는다. 새로운 팀원이 온보딩할 때도 유용하다.

**브랜치와 커밋 규칙**: PR(Pull Request) 전략, 커밋 메시지 형식, 브랜치 명명 규칙을 명시한다.

**버전 관리 규칙**: 스킬이나 패키지에 semver(Semantic Versioning, 의미론적 버전 관리)를 적용한다면 patch/minor/major 기준을 명시한다.

### 제외할 항목

**코드에서 이미 유추 가능한 정보**: `package.json`에 의존성이 명시되어 있다면 CLAUDE.md에 다시 나열할 필요가 없다. Claude는 이미 파일을 읽을 수 있다.

**표준 언어나 프레임워크 규칙**: TypeScript의 기본 문법, React의 훅 사용법 같은 언어 표준을 CLAUDE.md에 담지 않는다. Claude는 이미 알고 있다.

**자주 변하는 값**: 현재 버전 번호, 특정 이슈 번호, 임시 설정값은 파일에 하드코딩하면 금방 낡은 정보가 된다.

**자세한 API 문서**: 엔드포인트 목록이나 파라미터 설명은 별도 문서로 관리하고 CLAUDE.md에서 `@문법`으로 참조하는 편이 낫다.

### 실제 사례: wise-claude-code의 CLAUDE.md

이 레포지토리의 `CLAUDE.md`는 좋은 예시다. 핵심만 담고 있으면서도 Claude가 작업을 시작하는 데 필요한 정보를 모두 포함한다.

```markdown
# wise-claude-code

## Project
- Claude Code 커스텀 스킬 레포지토리
- 주 언어: 한국어 (커밋 메시지, 스킬 내용, 소통)
- 스킬 위치: `skills/` 디렉토리

## Skill 작성·수정·개선 규칙

스킬을 작성, 수정, 검토할 때는 반드시 `The-Complete-Guide-to-Building-Skill-for-Claude.pdf`를 먼저 읽고 해당 가이드의 규칙을 따른다.

### 버전 관리 규칙

모든 스킬은 SKILL.md frontmatter에 `version` 필드를 가진다. 스킬의 내용(SKILL.md, references/ 등)이 변경되면 반드시 버전을 올린다.

- **patch** (1.0.0 → 1.0.1): 오타 수정, 문구 다듬기 등 동작에 영향 없는 변경
- **minor** (1.0.0 → 1.1.0): 기능 추가, 템플릿 구조 변경, 지시문 개선 등 동작에 영향 있는 변경
- **major** (1.0.0 → 2.0.0): 스킬의 목적이나 워크플로우가 근본적으로 바뀌는 변경
```

이 파일이 효과적인 이유를 분석하면 다음과 같다.

- **프로젝트 성격을 한 줄로 정의**: "Claude Code 커스텀 스킬 레포지토리"라는 한 문장으로 Claude가 이 프로젝트의 목적을 즉시 파악한다.
- **주 언어 명시**: "한국어"라고 명시하지 않으면 Claude는 영어로 응답하기 쉽다. 커밋 메시지까지 한국어로 쓴다는 점도 분명히 밝힌다.
- **규칙의 이유 설명**: patch/minor/major 구분 기준을 예시와 함께 제시해 판단 기준을 명확히 한다.
- **참조 문서 안내**: 가이드 PDF 파일을 먼저 읽으라는 지침으로 작업 전 선행 조건을 명시한다.

## 파일 임포트: @ 문법

CLAUDE.md 안에서 `@파일경로` 형식으로 다른 파일을 참조할 수 있다. Claude가 해당 파일을 자동으로 읽어 컨텍스트에 포함한다.

```markdown
# 프로젝트 지침

@README.md
@package.json
@docs/architecture.md
```

### 활용 사례

**README 중복 방지**: 프로젝트 개요가 이미 README.md에 잘 정리되어 있다면 CLAUDE.md에 다시 쓰지 않고 `@README.md`로 참조한다.

**의존성 목록 자동 반영**: `@package.json`을 포함하면 Claude가 현재 사용 중인 라이브러리 버전을 정확히 알 수 있다. 직접 적은 버전 정보가 실제와 달라지는 문제를 방지한다.

**아키텍처 문서 분리**: 상세한 설계 결정 사항은 `@docs/architecture.md`처럼 별도 문서로 관리한다. CLAUDE.md는 간결하게 유지하면서도 필요한 문맥을 제공할 수 있다.

**API 스펙 참조**: `@openapi.yaml`을 포함하면 Claude가 엔드포인트 구조를 파악하고 구현이나 테스트를 작성할 때 활용한다.

## .claude/rules/ 디렉토리

큰 프로젝트에서 규칙을 하나의 CLAUDE.md에 모두 담으면 파일이 비대해진다. `.claude/rules/` 디렉토리를 사용하면 규칙을 모듈 단위로 분리하고 특정 경로에만 적용할 수 있다.

### 구조 예시

```
.claude/
  rules/
    backend.md          # 백엔드 전체에 적용
    frontend.md         # 프론트엔드 전체에 적용
    testing.md          # 테스트 파일에만 적용
    api-contracts.md    # API 관련 파일에만 적용
```

### frontmatter의 paths 필드

각 규칙 파일 상단에 YAML frontmatter(머리말)를 작성해 적용 범위를 지정한다.

```markdown
---
paths:
  - "src/api/**"
  - "src/routes/**"
---

# API 규칙

모든 엔드포인트는 반드시 입력값 유효성 검사를 포함해야 한다.
응답 형식은 `{ data, error, meta }` 구조를 따른다.
```

위 예시에서 이 규칙은 `src/api/` 와 `src/routes/` 하위 파일을 작업할 때만 Claude에게 로드된다. 다른 디렉토리 작업 시에는 컨텍스트를 차지하지 않는다.

paths를 지정하지 않으면 해당 규칙은 모든 파일 작업에 적용된다.

## 자동 메모리 (Auto Memory)

Claude Code는 세션 중에 학습한 내용을 자동으로 저장하는 기능을 제공한다. 사용자가 "이 프로젝트에서는 항상 이 방식을 사용해"라고 알려주면 Claude가 이를 기억해 다음 세션에도 적용할 수 있다.

### 저장 위치

자동 메모리는 다음 경로에 저장된다.

```
~/.claude/projects/<프로젝트-경로>/memory/
```

예를 들어 `/home/user/my-project`에서 작업하면 아래 경로에 메모리 파일이 생성된다.

```
~/.claude/projects/home-user-my-project/memory/
```

### 활성화와 비활성화

세션 내에서 `/memory` 명령으로 자동 메모리 기능을 켜거나 끌 수 있다.

영구적으로 비활성화하려면 `~/.claude/settings.json`에 다음을 추가한다.

```json
{
  "autoMemory": false
}
```

### 메모리의 네 가지 타입

Claude는 저장할 내용을 **무엇에 관한 정보인가**에 따라 네 종류로 분류한다. 각 타입은 별도의 파일로 저장되며, `type` 필드로 구분된다.

| 타입 | 저장 대상 | 언제 저장되는가 |
|---|---|---|
| `user` | 사용자의 역할, 목표, 책임, 배경 지식 | 사용자의 직무·숙련도·선호 표현 방식이 드러날 때 |
| `feedback` | 작업 방식에 대한 교정과 확인 | 사용자가 특정 접근을 바로잡거나(“그렇게 하지 마”), 비자명한 선택을 승인할 때 |
| `project` | 진행 중인 작업·일정·결정 배경 | 코드나 git 이력에서 유추할 수 없는 이유, 담당자, 마감이 드러날 때 |
| `reference` | 외부 시스템 위치 포인터 | Linear 프로젝트, Grafana 대시보드, Slack 채널 등 외부 자원을 언급할 때 |

네 타입을 분리하는 이유는 **재사용 시점이 서로 다르기 때문**이다. `user`는 거의 항상 참고 대상이고, `project`는 빠르게 낡으며, `feedback`은 같은 실수를 반복하지 않기 위해 반복적으로 읽혀야 한다. 섞어두면 어떤 것을 지금 꺼내 써야 할지 Claude가 판단하기 어렵다.

### 저장 포맷: frontmatter와 본문

각 메모리는 별도 마크다운 파일(`user_role.md`, `feedback_testing.md` 등)로 저장되며, 상단 frontmatter(머리말)와 본문으로 구성된다.

```markdown
---
name: {{메모리 이름}}
description: {{한 줄 설명 — 이후 대화에서 관련성 판단의 기준이 되므로 구체적으로}}
type: {{user | feedback | project | reference}}
---

{{본문}}
```

`feedback`과 `project` 타입은 본문 구조가 더 엄격하다. 규칙이나 사실을 먼저 한 문장으로 쓰고, 그 아래 **`**Why:**`** 라인과 **`**How to apply:**`** 라인을 둔다.

```markdown
---
name: 통합 테스트는 실제 DB에 붙인다
description: mock DB 금지 — 과거 사고 이후 실제 DB 사용 원칙
type: feedback
---

통합 테스트는 mock이 아니라 실제 데이터베이스에 연결해야 한다.
**Why:** 지난 분기에 mock은 통과했지만 prod 마이그레이션이 깨졌던 사고가 있었다.
**How to apply:** `tests/integration/` 아래 테스트를 작성·수정할 때.
```

Why를 함께 적는 이유는 **경계 사례 판단**을 위해서다. 규칙만 있으면 Claude는 예외 상황에서도 기계적으로 따르지만, 이유를 알면 새로운 상황이 그 규칙의 취지에 해당하는지 스스로 판단할 수 있다.

### MEMORY.md 인덱스

메모리 디렉토리에는 `MEMORY.md`라는 인덱스 파일이 반드시 하나 있다. 이 파일은 frontmatter가 없고, 각 메모리 파일로의 한 줄 포인터만 담는다.

```markdown
- [사용자 역할](user_role.md) — 10년차 백엔드, 이 레포의 프론트엔드는 처음
- [통합 테스트 DB 원칙](feedback_testing.md) — mock 금지, 과거 사고 기반
- [2026-04-30 배포 동결](project_merge_freeze.md) — 모바일 릴리스 컷 이후 비핵심 PR 금지
- [파이프라인 버그 트래커](reference_linear_ingest.md) — Linear 프로젝트 "INGEST"
```

규칙은 세 가지다.

- **한 줄당 하나의 메모리**, 150자 이내로 유지한다.
- **형식 고정**: `- [제목](파일.md) — 한 줄 훅`. 훅은 "왜 이 메모리가 존재하는지"를 한 문장으로 드러낸다.
- **전체 길이는 200줄 이내**. 200줄을 넘기면 뒷부분이 잘려나간다. 인덱스는 대화마다 자동으로 컨텍스트에 주입되기 때문에 간결함이 핵심이다.

`MEMORY.md`에 메모리 본문을 직접 쓰지 않는다. 어디까지나 **인덱스**다. 내용은 별도 파일에 두고, 여기서는 그 파일을 가리킬 뿐이다.

### 저장하지 말아야 할 것

메모리는 만능 노트가 아니다. 다음은 **이미 다른 곳에 더 정확하게 존재하는 정보**이므로 저장하지 않는다.

- **코드 패턴, 디렉토리 구조, 파일 경로** — 필요할 때 프로젝트를 읽으면 된다. 저장하면 리팩토링과 함께 낡는다.
- **git 이력, 최근 변경 내역, 누가 무엇을 바꿨는지** — `git log`, `git blame`이 원본이다.
- **디버깅 해결책, 버그 수정 레시피** — 수정된 코드 자체가 답이고, 커밋 메시지에 맥락이 남는다.
- **CLAUDE.md에 이미 적힌 내용** — 중복은 상충 가능성만 만든다.
- **지금 대화의 진행 상황, 임시 상태** — 세션 내 작업은 TODO나 Plan으로 관리한다.

사용자가 "방금 한 작업 요약을 저장해달라"고 해도 그대로 저장하지 않는다. 그 중 **무엇이 의외였는지, 무엇이 비자명했는지**만 추려 저장하는 것이 올바른 사용법이다.

### 검증 원칙: 저장된 메모리는 "예전에 맞았던 사실"이다

메모리는 작성 시점의 스냅샷이다. 함수 이름, 파일 경로, 설정 플래그는 그 사이에 바뀌었거나 제거됐을 수 있다. Claude가 메모리를 근거로 뭔가를 제안하기 전에 다음을 확인하도록 한다.

- 메모리가 파일 경로를 언급하면 → 그 파일이 **지금** 존재하는지 확인한다.
- 메모리가 함수·플래그 이름을 언급하면 → `grep`으로 현존 여부를 확인한다.
- 사용자가 **현재 상태**에 대해 묻는 경우(“요즘 어디까지 됐어?”) → 메모리 대신 `git log`와 실제 코드를 먼저 읽는다.

"메모리에 X가 있다고 적혀 있다"와 "X가 지금 존재한다"는 다르다. 상충이 발견되면 지금 관찰한 쪽을 신뢰하고, 낡은 메모리는 갱신하거나 삭제한다.

### 플랜·태스크와의 경계

메모리는 **다음 세션까지 살아남아야 할 정보**만 담는다. 현재 대화 안에서만 유효한 정보는 다른 수단으로 관리한다.

| 수단 | 쓰임새 |
|---|---|
| **메모리** | 다음 세션에서도 유효한 개인 맥락, 교정, 프로젝트 배경 |
| **Plan** | 비자명한 구현을 시작하기 전 접근을 합의할 때 |
| **Task 목록** | 지금 대화에서의 단계별 진행 상태 |
| **CLAUDE.md** | 팀 전체에 적용되고 git으로 공유되는 규칙 |

구현 접근을 바꿨다면 플랜을 고치는 것이 맞지, 메모리에 남길 일이 아니다. 마찬가지로 "이번 PR에서 할 일"은 태스크이지 메모리가 아니다.

### CLAUDE.md와의 차이

CLAUDE.md는 개발자가 의도적으로 작성하는 지침이다. 팀 전체에 적용되며 git으로 관리된다. 자동 메모리는 Claude가 대화를 통해 학습한 개인 설정이다. 특정 사용자의 작업 스타일에 맞춰지며 git에 올라가지 않는다.

중요한 팀 규칙은 CLAUDE.md에 명시적으로 작성해야 한다. 자동 메모리에만 의존하면 새로운 팀원이나 CI(Continuous Integration, 지속적 통합) 환경에서는 해당 규칙을 인식하지 못한다.

| 항목 | CLAUDE.md | 자동 메모리 |
|---|---|---|
| 주체 | 개발자가 직접 작성 | Claude가 대화에서 추출 |
| 범위 | 팀·프로젝트 전체 | 개인 |
| 저장소 | git에 커밋 | `~/.claude/` 로컬 |
| 수명 | 영구 | 낡으면 갱신·삭제 |
| 적합한 내용 | 구조적 규칙, 명령어, 컨벤션 | 개인 배경, 과거 교정, 진행 중 맥락 |

## 흔한 실수

### CLAUDE.md가 너무 길다

100줄짜리 CLAUDE.md도 충분히 길다. 200줄을 넘어서면 실제로 대화에 사용할 수 있는 컨텍스트가 눈에 띄게 줄어든다. 항목마다 "꼭 Claude가 알아야 하는가?"를 따져본 뒤 불필요한 내용은 제거한다. 상세한 설명이 필요한 항목은 `@문법`으로 외부 파일을 참조하는 방식으로 분리한다.

### 코드에서 이미 알 수 있는 정보를 반복한다

`tsconfig.json`에 `strict: true`가 설정되어 있다면 "TypeScript strict 모드를 사용한다"를 CLAUDE.md에 다시 적을 필요가 없다. Claude는 설정 파일을 직접 읽을 수 있다. 파일만 봐서는 알기 어려운 팀 내부의 합의 사항과 결정 배경에 집중한다.

### 자주 변하는 정보를 하드코딩한다

"현재 스프린트 목표는 결제 모듈 완성이다" 같은 내용은 CLAUDE.md에 적합하지 않다. 며칠 뒤 낡은 정보가 된다. CLAUDE.md는 수개월이 지나도 유효한 구조적 지침을 담는 곳이다. 단기적인 작업 지시는 대화 중에 직접 전달한다.

### 규칙의 이유를 생략한다

"외부 라이브러리 추가 금지"라고만 쓰면 Claude가 맥락 없이 규칙을 적용하다가 불필요한 마찰이 생긴다. "번들 크기 제한으로 인해 외부 라이브러리 추가 시 반드시 사전 검토가 필요하다"처럼 이유를 함께 쓰면 Claude가 예외 상황을 올바르게 판단할 수 있다.

- [ ] 프로젝트 레벨 파일은 git에 커밋되어 있는가?
- [ ] 개인 설정은 `~/.claude/CLAUDE.md`에 분리했는가?
