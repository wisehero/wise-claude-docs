Claude Code 실전 가이드

Claude Code 설치부터 하네스 엔지니어링까지, 여덟 편의 한국어 문서를 하나의 HTML로 묶은 허브입니다. 훅 시스템 챕터에는 인터랙티브 시각 자료가 포함되어 있습니다.

사용 안내

좌측 목차의 챕터 번호로 문서 사이를 이동합니다. 하위 섹션은 각 챕터 아래 펼쳐져 있습니다. 코드 블록 우측 상단의 복사 버튼을 누르면 코드가 클립보드로 복사됩니다. 훅 시스템 챕터의 인터랙티브 블록은 요소를 클릭해 세부 정보를 엽니다.

Chapter 01

Claude Code 시작하기

문서 메타

난이도: 기초 | 선행 문서: 없음

Claude Code의 설치부터 첫 세션까지, 빠르게 시작하는 데 필요한 모든 것을 다룬다.

Claude Code란?

Claude Code는 Anthropic이 공식 배포하는 CLI(Command-Line Interface, 명령줄 인터페이스) 도구다. 터미널에서 Claude와 직접 대화하면서 코드 작성, 파일 편집, git 작업, 테스트 실행 등 개발 워크플로 전반을 처리할 수 있다.

웹 브라우저에서 쓰는 claude.ai와 달리 Claude Code는 현재 작업 중인 코드베이스 위에서 동작한다. 파일을 직접 읽고, 셸 명령을 실행하며, 변경 사항을 파일에 바로 쓴다. 개발자에게 필요한 작업 대부분을 터미널을 벗어나지 않고 처리할 수 있다는 점이 핵심이다.

사용 가능한 인터페이스

Claude Code는 여러 형태로 제공된다.

  • CLI: 터미널에서 claude 명령으로 실행하는 기본 형태
  • 데스크톱 앱: 독립 실행형 네이티브 앱
  • 웹 앱: claude.ai/code에서 브라우저로 접근
  • IDE 확장: VS Code와 JetBrains 계열 IDE에서 패널로 사용

이 문서는 CLI를 기준으로 설명한다. 핵심 개념과 명령어는 다른 인터페이스에도 그대로 적용된다.

설치

macOS / Linux

터미널에서 아래 명령을 실행한다.

curl -fsSL https://claude.ai/install.sh | bash

설치 스크립트가 Node.js 버전을 확인하고, Claude Code 바이너리를 내려받아 PATH에 등록한다. 완료 후 새 터미널 탭을 열거나 source ~/.bashrc(또는 ~/.zshrc)를 실행해 PATH를 갱신한다.

Homebrew를 선호한다면 아래 방법도 사용할 수 있다.

brew install --cask claude-code

단, Homebrew를 통한 설치는 자동 업데이트가 지원되지 않는다. 최신 버전을 유지하려면 주기적으로 brew upgrade --cask claude-code를 실행해야 한다.

Windows

PowerShell을 관리자 권한으로 열고 실행한다.

irm https://claude.ai/install.ps1 | iex

명령 프롬프트(CMD)에서 설치하려면 공식 문서를 참고한다.

WinGet을 사용하는 경우 아래 명령으로 설치할 수 있다.

winget install Anthropic.ClaudeCode

Homebrew와 마찬가지로 WinGet 설치본도 자동 업데이트가 지원되지 않는다.

Windows 사용 시 주의 사항: Claude Code는 내부적으로 git 명령을 사용하므로 Git for Windows가 반드시 설치되어 있어야 한다. git-scm.com에서 내려받을 수 있다.

설치 확인

설치가 끝나면 버전을 확인해 정상적으로 설치됐는지 점검한다.

claude --version

버전 번호가 출력되면 설치가 완료된 것이다.

인증 및 로그인

Claude Code를 처음 실행하면 로그인 절차가 시작된다.

claude

또는 대화 세션 중에 슬래시 명령으로 로그인할 수 있다.

/login

지원하는 계정 유형

계정 유형 설명
Claude Pro / Max claude.ai 개인 구독
Claude Teams / Enterprise 팀 및 기업 구독
Claude Console (API) Anthropic API 키를 통한 직접 접근
Amazon Bedrock AWS에서 호스팅하는 Claude 모델
Google Vertex AI GCP에서 호스팅하는 Claude 모델

Pro 또는 Max 구독자라면 브라우저 OAuth(개방형 인증) 흐름으로 로그인한다. API 키를 사용하는 경우 Console에서 발급한 키를 입력한다. Bedrock과 Vertex AI는 각 클라우드 제공업체의 자격증명 설정이 선행되어야 한다.

기본 명령어

Claude Code를 사용하는 방식은 크게 세 가지다.

인터랙티브 세션(대화형 세션)

claude

REPL(Read-Eval-Print Loop, 읽기-평가-출력 반복) 환경이 열린다. 여기서 자연어로 요청을 입력하면 Claude가 파일을 읽고, 코드를 작성하고, 명령을 실행한다. 세션을 종료하려면 exit를 입력하거나 Ctrl+C를 두 번 누른다.

일회성 작업

claude "README.md 파일을 읽고 주요 기능을 세 줄로 요약해줘"

세션을 열지 않고 단일 작업을 처리한다. 결과를 출력하고 종료된다. 스크립트나 파이프라인에 Claude를 끼워 넣을 때 유용하다.

쿼리 후 종료

claude -p "이 프로젝트의 주요 의존성은 무엇인가?"

-p 플래그(print 모드)는 단일 질의를 처리하고 결과를 표준 출력으로 내보낸 뒤 종료한다. 다른 명령의 출력을 파이프로 연결할 때 활용한다.

이전 대화 재개

claude -c          # 가장 최근 대화 이어서 시작
claude -r          # 이전 대화 목록에서 선택해 재개

Claude Code는 대화 기록을 저장한다. 어제 작업하던 컨텍스트(문맥)를 그대로 이어서 사용할 수 있다.

Git 커밋 생성

claude commit

현재 스테이징된 변경 사항을 분석해 커밋 메시지를 작성하고 커밋한다. 메시지를 직접 작성하지 않아도 된다.

세션 내 슬래시 명령

인터랙티브 세션 안에서 /로 시작하는 명령을 사용할 수 있다.

명령 설명
/help 사용 가능한 명령 목록 표시
/clear 현재 대화 컨텍스트 초기화
/init 현재 프로젝트에 CLAUDE.md 파일 생성
/login 계정 로그인
exit 세션 종료

권한 모드(Permission Modes)

Claude Code는 파일 쓰기, 명령 실행 등 실제 시스템에 영향을 주는 작업을 수행한다. 권한 모드는 Claude가 작업을 수행하기 전에 사용자 확인을 얼마나 요구할지 결정한다.

세 가지 모드

default 모드: 잠재적 위험이 있는 모든 작업에 대해 확인을 요청한다. 파일 수정, 명령 실행 등을 수행하기 전에 "허용할까요?"라는 프롬프트가 표시된다. 처음 사용하거나 낯선 코드베이스에서 작업할 때 권장한다.

plan 모드: 읽기 전용 분석 모드다. 파일을 읽고 계획을 세우는 작업만 수행하며 실제 변경을 가하지 않는다. 변경 전에 Claude가 무엇을 할지 미리 파악하고 싶을 때 사용한다.

auto 모드: Claude가 위험도를 자체 판단해 안전하다고 판단한 작업은 확인 없이 진행한다. 반복적인 승인 클릭 없이 빠르게 작업하고 싶을 때 유용하지만, 예상치 못한 변경이 발생할 수 있으므로 주의가 필요하다.

모드 전환

세션 중 Shift+Tab을 누르면 모드를 순환 전환할 수 있다. 현재 활성 모드는 프롬프트 옆에 표시된다.

자주 쓰는 도구 자동 허용

매번 특정 도구의 실행을 허용하는 것이 번거롭다면 설정 파일에 allowedTools 항목을 추가한다. 예를 들어 Bash 도구를 항상 허용하도록 설정할 수 있다. 이 설정은 아래에서 설명하는 설정 파일 구조를 통해 적용한다. 권한 설정의 세부 옵션은 공식 문서를 참고한다.

설정 파일 구조

Claude Code의 동작은 JSON 설정 파일로 제어한다. 파일 위치에 따라 적용 범위가 달라진다.

글로벌 설정

~/.claude/settings.json

모든 프로젝트에 공통으로 적용되는 설정이다. 선호하는 모델, 기본 권한 모드, API 키 등 사용자 수준 설정을 여기에 저장한다.

프로젝트 설정

.claude/settings.json

특정 프로젝트 루트에 위치하며 git에 커밋해 팀과 공유한다. 프로젝트에 특화된 허용 도구 목록, 환경 변수 등을 정의한다.

프로젝트 로컬 설정

.claude/settings.local.json

프로젝트별이지만 git에 올리지 않는 개인 설정이다. .gitignore에 자동으로 추가된다. API 키처럼 공유하면 안 되는 값이나 개인 취향 설정을 여기에 저장한다.

주요 설정 항목

{
  "model": "claude-opus-4-7",
  "permissions": {
    "allow": ["Bash(git:*)"],
    "deny": []
  },
  "env": {
    "CLAUDE_SKIP_PERMISSIONS": "false"
  }
}

설정 파일의 전체 옵션은 프로젝트 지침 파일인 CLAUDE.md와 함께 사용할 때 진가를 발휘한다. CLAUDE.md에 대한 자세한 내용은 02-CLAUDE-md-작성-가이드.md에서 다룬다.

첫 세션 체크리스트

아래 순서로 따라가면 Claude Code를 빠르게 시작할 수 있다.

1단계: 설치 및 로그인 확인

claude --version   # 설치 확인
claude             # 세션 시작 및 로그인

처음 실행하면 로그인 절차가 자동으로 안내된다. 브라우저가 열리며 Anthropic 계정으로 인증한다.

2단계: 프로젝트 초기화

작업할 프로젝트 디렉토리로 이동한 뒤 세션을 열고 /init을 실행한다.

cd my-project
claude

세션 안에서:

/init

/init은 현재 코드베이스를 분석해 CLAUDE.md 파일을 생성한다. 이 파일은 Claude가 프로젝트를 이해하는 데 사용하는 지침 문서다. 생성된 내용을 검토하고 팀 컨벤션(코딩 규칙)이나 주의 사항을 직접 추가하면 된다.

3단계: 첫 번째 작업 실행

간단한 작업으로 시작해본다.

이 프로젝트의 디렉토리 구조를 설명해줘

Claude가 파일을 탐색하며 프로젝트 구조를 파악하고 설명한다. 필요에 따라 권한 확인 프롬프트가 표시된다.

다음으로 실질적인 작업을 시도한다.

src/utils.js 파일에서 중복된 함수가 있는지 확인하고 정리해줘

Claude가 파일을 읽고 중복을 찾은 뒤, 변경 사항을 적용하기 전에 확인을 요청한다(default 모드 기준). 내용을 검토하고 허용 여부를 결정한다.

핵심 정리

  • Claude Code는 터미널에서 동작하는 Anthropic 공식 CLI로, 코드베이스에 직접 접근해 파일 편집과 명령 실행을 수행한다.
  • 설치는 플랫폼별 단일 명령으로 완료되며, Windows에서는 Git for Windows가 선행 설치되어야 한다.
  • Pro / Max / Teams / Enterprise 구독과 Anthropic API, Bedrock, Vertex AI를 통한 접근을 모두 지원한다.
  • 권한 모드(default / plan / auto)로 Claude의 자율성 수준을 조절하며, Shift+Tab으로 즉시 전환할 수 있다.
  • 설정 파일은 글로벌(~/.claude/settings.json), 프로젝트(.claude/settings.json), 로컬(.claude/settings.local.json) 세 계층으로 나뉜다.
  • 새 프로젝트를 시작할 때는 /init으로 CLAUDE.md를 먼저 생성한다.

Chapter 02

CLAUDE.md 작성 가이드

문서 메타

난이도: 기초~중급 | 선행 문서: Claude Code 시작하기

프로젝트의 맥락과 규칙을 Claude에게 전달하는 CLAUDE.md의 작성법과 계층 구조를 다룬다.

CLAUDE.md란?

Claude Code는 세션을 시작할 때 작업 디렉토리를 탐색해 CLAUDE.md 파일을 찾고 자동으로 읽는다. 이 파일은 Claude에게 "이 프로젝트에서 어떻게 행동해야 하는가"를 알려주는 지침서다.

코드베이스의 규모가 클수록, 팀 컨벤션(코딩 규칙)이 복잡할수록 CLAUDE.md의 역할이 중요해진다. Claude는 파일을 직접 읽어 언어나 프레임워크의 패턴을 어느 정도 유추할 수 있지만, 다음과 같은 것은 파일만 보고 알기 어렵다.

  • 팀이 선호하는 브랜치 전략이나 커밋 메시지 형식
  • 특정 라이브러리 대신 자체 유틸리티를 써야 하는 이유
  • 테스트를 실행하는 정확한 명령과 플래그
  • 배포 전 반드시 통과해야 하는 체크리스트

이런 맥락을 CLAUDE.md에 명시하면 Claude는 매 세션마다 동일한 수준의 이해를 갖고 작업을 시작한다.

시스템 프롬프트와의 관계

CLAUDE.md는 사실상 프로젝트 전용 시스템 프롬프트로 동작한다. Claude Code는 이 파일의 내용을 컨텍스트(문맥) 창의 초반부에 주입한다. 따라서 지침이 길고 상세할수록 실제 작업에 쓸 수 있는 컨텍스트가 줄어든다. 시스템 프롬프트 설계의 원칙에 대해서는 claude/03-시스템-프롬프트-설계.md를 참조한다.

계층 구조

CLAUDE.md는 네 개의 계층으로 동작하며, 계층마다 적용 범위와 관리 주체가 다르다.

1. 관리 정책 레벨 (Enterprise)

조직 관리자가 설정하는 최상위 계층이다. 개별 사용자가 덮어쓸 수 없으며, 보안 정책이나 준수해야 할 사내 규정을 배포할 때 사용한다.

저장 위치는 운영 체제별로 다르다.

OS 경로
macOS /Library/Application Support/ClaudeCode/CLAUDE.md
Linux /etc/claude-code/CLAUDE.md
Windows C:\Program Files\ClaudeCode\CLAUDE.md

2. 프로젝트 레벨

가장 자주 사용하는 계층이다. 두 위치 중 하나에 파일을 두면 된다.

./CLAUDE.md              # 프로젝트 루트
./.claude/CLAUDE.md      # .claude 디렉토리 안

이 파일은 git에 커밋해 팀 전체가 공유한다. 프로젝트의 코딩 스타일, 테스트 방법, 아키텍처 결정 등 팀 전체에 적용할 지침을 담는다.

3. 하위 디렉토리 레벨

프로젝트의 하위 디렉토리에 CLAUDE.md 파일을 추가로 둘 수 있다. Claude가 해당 디렉토리의 파일을 작업할 때 온디맨드(on-demand)로 로드된다. 대규모 모노레포에서 서비스별로 다른 지침을 적용할 때 유용하다.

4. 사용자 레벨

특정 프로젝트가 아닌 사용자 개인에게 항상 적용되는 설정이다.

~/.claude/CLAUDE.md

자신만의 작업 스타일, 선호하는 출력 형식, 개인적인 워크플로 지침을 저장한다. 팀의 CLAUDE.md와 충돌하면 팀 설정이 우선한다.

우선순위

관리 정책 > 프로젝트 > 하위 디렉토리 > 사용자

하위 계층의 지침이 상위 계층과 충돌하면 상위 계층이 이긴다. 각 계층의 내용은 합산되어 Claude에게 전달되므로, 중복 없이 적절한 계층에 지침을 배치하는 것이 중요하다.

효과적인 CLAUDE.md 작성

목표 크기

200줄 미만을 목표로 한다. CLAUDE.md는 Claude의 컨텍스트 창을 직접 소비하기 때문에 길수록 실제 작업 공간이 줄어든다. 긴 파일이 필요하다면 아래에서 설명하는 @문법을 사용해 외부 파일로 분리한다.

포함할 항목

자주 쓰는 Bash 명령어: 테스트 실행, 빌드, 린트 등 반복적으로 사용하는 명령을 명시한다. Claude가 추측 없이 올바른 명령을 사용할 수 있다.

코드 스타일과 컨벤션: 자동 포매터로 강제되지 않는 팀 고유의 규칙을 적는다. "함수는 명사형이 아닌 동사형으로 시작한다", "에러 처리는 반드시 커스텀 AppError 클래스를 사용한다" 같은 내용이 해당된다.

아키텍처 결정: 특정 패턴을 선택한 이유나 피해야 할 접근 방식을 적는다. 새로운 팀원이 온보딩할 때도 유용하다.

브랜치와 커밋 규칙: PR(Pull Request) 전략, 커밋 메시지 형식, 브랜치 명명 규칙을 명시한다.

버전 관리 규칙: 스킬이나 패키지에 semver(Semantic Versioning, 의미론적 버전 관리)를 적용한다면 patch/minor/major 기준을 명시한다.

제외할 항목

코드에서 이미 유추 가능한 정보: package.json에 의존성이 명시되어 있다면 CLAUDE.md에 다시 나열할 필요가 없다. Claude는 이미 파일을 읽을 수 있다.

표준 언어나 프레임워크 규칙: TypeScript의 기본 문법, React의 훅 사용법 같은 언어 표준을 CLAUDE.md에 담지 않는다. Claude는 이미 알고 있다.

자주 변하는 값: 현재 버전 번호, 특정 이슈 번호, 임시 설정값은 파일에 하드코딩하면 금방 낡은 정보가 된다.

자세한 API 문서: 엔드포인트 목록이나 파라미터 설명은 별도 문서로 관리하고 CLAUDE.md에서 @문법으로 참조하는 편이 낫다.

실제 사례: wise-claude-code의 CLAUDE.md

이 레포지토리의 CLAUDE.md는 좋은 예시다. 핵심만 담고 있으면서도 Claude가 작업을 시작하는 데 필요한 정보를 모두 포함한다.

# wise-claude-code

## Project
- Claude Code 커스텀 스킬 레포지토리
- 주 언어: 한국어 (커밋 메시지, 스킬 내용, 소통)
- 스킬 위치: `skills/` 디렉토리

## Skill 작성·수정·개선 규칙

스킬을 작성, 수정, 검토할 때는 반드시 `The-Complete-Guide-to-Building-Skill-for-Claude.pdf`를 먼저 읽고 해당 가이드의 규칙을 따른다.

### 버전 관리 규칙

모든 스킬은 SKILL.md frontmatter에 `version` 필드를 가진다. 스킬의 내용(SKILL.md, references/ 등)이 변경되면 반드시 버전을 올린다.

- **patch** (1.0.0 → 1.0.1): 오타 수정, 문구 다듬기 등 동작에 영향 없는 변경
- **minor** (1.0.0 → 1.1.0): 기능 추가, 템플릿 구조 변경, 지시문 개선 등 동작에 영향 있는 변경
- **major** (1.0.0 → 2.0.0): 스킬의 목적이나 워크플로우가 근본적으로 바뀌는 변경

이 파일이 효과적인 이유를 분석하면 다음과 같다.

  • 프로젝트 성격을 한 줄로 정의: "Claude Code 커스텀 스킬 레포지토리"라는 한 문장으로 Claude가 이 프로젝트의 목적을 즉시 파악한다.
  • 주 언어 명시: "한국어"라고 명시하지 않으면 Claude는 영어로 응답하기 쉽다. 커밋 메시지까지 한국어로 쓴다는 점도 분명히 밝힌다.
  • 규칙의 이유 설명: patch/minor/major 구분 기준을 예시와 함께 제시해 판단 기준을 명확히 한다.
  • 참조 문서 안내: 가이드 PDF 파일을 먼저 읽으라는 지침으로 작업 전 선행 조건을 명시한다.

파일 임포트: @ 문법

CLAUDE.md 안에서 @파일경로 형식으로 다른 파일을 참조할 수 있다. Claude가 해당 파일을 자동으로 읽어 컨텍스트에 포함한다.

# 프로젝트 지침

@README.md
@package.json
@docs/architecture.md

활용 사례

README 중복 방지: 프로젝트 개요가 이미 README.md에 잘 정리되어 있다면 CLAUDE.md에 다시 쓰지 않고 @README.md로 참조한다.

의존성 목록 자동 반영: @package.json을 포함하면 Claude가 현재 사용 중인 라이브러리 버전을 정확히 알 수 있다. 직접 적은 버전 정보가 실제와 달라지는 문제를 방지한다.

아키텍처 문서 분리: 상세한 설계 결정 사항은 @docs/architecture.md처럼 별도 문서로 관리한다. CLAUDE.md는 간결하게 유지하면서도 필요한 문맥을 제공할 수 있다.

API 스펙 참조: @openapi.yaml을 포함하면 Claude가 엔드포인트 구조를 파악하고 구현이나 테스트를 작성할 때 활용한다.

.claude/rules/ 디렉토리

큰 프로젝트에서 규칙을 하나의 CLAUDE.md에 모두 담으면 파일이 비대해진다. .claude/rules/ 디렉토리를 사용하면 규칙을 모듈 단위로 분리하고 특정 경로에만 적용할 수 있다.

구조 예시

.claude/
  rules/
    backend.md          # 백엔드 전체에 적용
    frontend.md         # 프론트엔드 전체에 적용
    testing.md          # 테스트 파일에만 적용
    api-contracts.md    # API 관련 파일에만 적용

frontmatter의 paths 필드

각 규칙 파일 상단에 YAML frontmatter(머리말)를 작성해 적용 범위를 지정한다.

---
paths:
  - "src/api/**"
  - "src/routes/**"
---

# API 규칙

모든 엔드포인트는 반드시 입력값 유효성 검사를 포함해야 한다.
응답 형식은 `{ data, error, meta }` 구조를 따른다.

위 예시에서 이 규칙은 src/api/ 와 src/routes/ 하위 파일을 작업할 때만 Claude에게 로드된다. 다른 디렉토리 작업 시에는 컨텍스트를 차지하지 않는다.

paths를 지정하지 않으면 해당 규칙은 모든 파일 작업에 적용된다.

자동 메모리 (Auto Memory)

Claude Code는 세션 중에 학습한 내용을 자동으로 저장하는 기능을 제공한다. 사용자가 "이 프로젝트에서는 항상 이 방식을 사용해"라고 알려주면 Claude가 이를 기억해 다음 세션에도 적용할 수 있다.

저장 위치

자동 메모리는 다음 경로에 저장된다.

~/.claude/projects/<프로젝트-경로>/memory/

예를 들어 /home/user/my-project에서 작업하면 아래 경로에 메모리 파일이 생성된다.

~/.claude/projects/home-user-my-project/memory/

활성화와 비활성화

세션 내에서 /memory 명령으로 자동 메모리 기능을 켜거나 끌 수 있다.

영구적으로 비활성화하려면 ~/.claude/settings.json에 다음을 추가한다.

{
  "autoMemory": false
}

CLAUDE.md와의 차이

CLAUDE.md는 개발자가 의도적으로 작성하는 지침이다. 팀 전체에 적용되며 git으로 관리된다. 자동 메모리는 Claude가 대화를 통해 학습한 개인 설정이다. 특정 사용자의 작업 스타일에 맞춰지며 git에 올라가지 않는다.

중요한 팀 규칙은 CLAUDE.md에 명시적으로 작성해야 한다. 자동 메모리에만 의존하면 새로운 팀원이나 CI(Continuous Integration, 지속적 통합) 환경에서는 해당 규칙을 인식하지 못한다.

흔한 실수

CLAUDE.md가 너무 길다

100줄짜리 CLAUDE.md도 충분히 길다. 200줄을 넘어서면 실제로 대화에 사용할 수 있는 컨텍스트가 눈에 띄게 줄어든다. 항목마다 "꼭 Claude가 알아야 하는가?"를 따져본 뒤 불필요한 내용은 제거한다. 상세한 설명이 필요한 항목은 @문법으로 외부 파일을 참조하는 방식으로 분리한다.

코드에서 이미 알 수 있는 정보를 반복한다

tsconfig.json에 strict: true가 설정되어 있다면 "TypeScript strict 모드를 사용한다"를 CLAUDE.md에 다시 적을 필요가 없다. Claude는 설정 파일을 직접 읽을 수 있다. 파일만 봐서는 알기 어려운 팀 내부의 합의 사항과 결정 배경에 집중한다.

자주 변하는 정보를 하드코딩한다

"현재 스프린트 목표는 결제 모듈 완성이다" 같은 내용은 CLAUDE.md에 적합하지 않다. 며칠 뒤 낡은 정보가 된다. CLAUDE.md는 수개월이 지나도 유효한 구조적 지침을 담는 곳이다. 단기적인 작업 지시는 대화 중에 직접 전달한다.

규칙의 이유를 생략한다

"외부 라이브러리 추가 금지"라고만 쓰면 Claude가 맥락 없이 규칙을 적용하다가 불필요한 마찰이 생긴다. "번들 크기 제한으로 인해 외부 라이브러리 추가 시 반드시 사전 검토가 필요하다"처럼 이유를 함께 쓰면 Claude가 예외 상황을 올바르게 판단할 수 있다.

핵심 정리

CLAUDE.md 작성 체크리스트다.

  • 파일이 200줄 미만인가?
  • 프로젝트의 목적이 첫 단락에 명확히 드러나는가?
  • 자주 쓰는 명령어(테스트, 빌드, 린트)가 정확히 기재되어 있는가?
  • 코드에서 유추할 수 없는 팀 고유의 규칙을 담고 있는가?
  • 각 규칙에 이유 또는 배경이 함께 설명되어 있는가?
  • 자주 변하는 정보는 제거했는가?
  • 긴 참조 문서는 @문법으로 분리했는가?
  • 프로젝트 레벨 파일은 git에 커밋되어 있는가?
  • 개인 설정은 ~/.claude/CLAUDE.md에 분리했는가?

문서 메타

Claude Code의 기능을 확장하는 커스텀 스킬의 구조, 작성법, 트리거 설정을 다룬다.

1. 스킬이란?

스킬(Skill)은 Claude Code에 새로운 능력을 추가하는 재사용 가능한 지시문 묶음이다. 특정 작업을 반복할 때마다 긴 프롬프트를 입력하는 대신, 스킬로 정의해두면 짧은 명령 하나로 동일한 작업을 실행할 수 있다.

스킬은 두 가지 방식으로 호출된다.

첫째, /skill-name 형태의 슬래시 명령어로 직접 호출한다. 사용자가 /spec-writer라고 입력하면 해당 스킬이 즉시 실행된다.

둘째, Claude가 대화 맥락을 보고 자동으로 감지하여 호출한다. "요구사항 명세서 작성해줘"라고 입력하면 Claude가 spec-writer 스킬을 자동으로 선택한다. 이 자동 감지 동작은 frontmatter의 description 필드가 결정한다.

스킬은 단순한 템플릿이 아니다. 도구 사용 권한, 모델 선택, 다단계 워크플로우, 외부 파일 참조까지 포함하는 독립적인 실행 단위다. CLAUDE.md가 프로젝트 전반의 행동 지침을 담는다면, 스킬은 특정 작업 유형에 특화된 절차와 지식을 캡슐화한다. 두 파일은 상호 보완적으로 작동한다.

스킬을 만들면 얻는 이점은 명확하다. 작업 품질이 일정해진다. Claude에게 매번 "SRS는 IEEE 830 기준으로, FR에는 선행 조건과 예외 흐름을 포함하고..."라고 설명하지 않아도 된다. 스킬에 이미 담겨 있다. 팀에서 스킬을 공유하면 여러 사람이 동일한 절차로 동일한 품질의 산출물을 만들 수 있다.

2. 스킬 디렉토리 구조

설치 위치

스킬은 두 곳에 설치할 수 있다.

  • ~/.claude/skills/: 모든 프로젝트에서 사용하는 글로벌 스킬
  • .claude/skills/: 현재 프로젝트에서만 사용하는 프로젝트 스킬

프로젝트 스킬은 글로벌 스킬보다 우선 적용된다. 같은 이름의 스킬이 두 곳에 모두 있으면 프로젝트 스킬이 사용된다. 이 우선순위 덕분에 글로벌 스킬을 기반으로 깔아두고, 프로젝트마다 특성에 맞게 오버라이드할 수 있다.

이 프로젝트(wise-claude-code)처럼 스킬 자체를 관리하는 레포지토리라면 skills/ 디렉토리를 루트에 두고 버전 관리한다. Claude Code는 skills/ 디렉토리도 인식한다.

파일 구성

각 스킬은 이름과 같은 디렉토리 안에 구성된다.

skill-name/
├── SKILL.md          # 메인 지시문 (필수)
├── references/       # 템플릿, 카탈로그 등 보조 파일
└── examples/         # 예시 결과물

SKILL.md만 필수다. references/와 examples/는 스킬의 복잡도에 따라 선택적으로 추가한다. 간단한 스킬은 SKILL.md 하나로 완결되고, 복잡한 스킬은 references/에 방대한 지식 베이스를 분리하여 관리한다.

이 프로젝트의 실제 구조

이 프로젝트(wise-claude-code)의 skills/ 디렉토리는 다음과 같이 구성되어 있다.

skills/
├── code-analyzer/
│   ├── SKILL.md
│   └── references/
│       └── report-template.md
├── humanizer/
│   └── SKILL.md
├── humanizer-korean/
│   └── SKILL.md
├── junit-test-writer/
│   ├── SKILL.md
│   └── references/
│       └── conventions.md
├── performance-profiler/
│   ├── SKILL.md
│   └── references/
│       ├── db-patterns.md
│       ├── algorithm-patterns.md
│       ├── memory-patterns.md
│       └── api-patterns.md
├── refactor-advisor/
│   ├── SKILL.md
│   └── references/
├── spec-writer/
│   ├── SKILL.md
│   └── references/
│       ├── srs-template.md
│       └── interview-guide.md
└── study-helper/
    ├── SKILL.md
    └── references/
        └── report-template.md

humanizer와 humanizer-korean은 SKILL.md 하나로 완결된다. AI 글쓰기 패턴 카탈로그를 SKILL.md 본문에 직접 포함하는 방식을 택했다. 반면 performance-profiler는 references/에 패턴 카탈로그 4개를 분리하여 관리한다. DB 쿼리, 알고리즘 복잡도, 메모리 사용, API 응답 시간 — 각 영역의 패턴이 방대하기 때문이다.

study-helper는 다른 스킬을 의존한다. 내부에서 /humanizer와 /external-context를 호출하는 복합 스킬이다. 스킬 간 의존 관계를 설계할 때는 SKILL.md의 "의존 스킬" 섹션에 명시하는 것이 관례다.

3. SKILL.md Frontmatter

SKILL.md 파일은 YAML frontmatter로 시작한다. 이 메타데이터가 스킬의 동작 방식을 제어한다.

필드 정리

필드 필수 여부 설명
name 필수 스킬 식별자. 디렉토리 이름과 일치시키는 것이 관례
description 권장 자동 감지의 핵심. 언제 이 스킬을 써야 하는지, 어떤 요청 표현에 반응하는지를 상세히 기술
version 선택 스킬 버전. 1.0.0 형식의 시맨틱 버전. 공식 스펙이 아닌 프로젝트 자체 컨벤션이지만, 변경 이력 추적에 유용하다
argument-hint 선택 슬래시 명령어 자동완성 시 표시되는 인자 힌트 텍스트
disable-model-invocation 선택 true로 설정하면 Claude가 자동 호출하지 않고 수동 슬래시 명령어로만 실행 가능
user-invocable 선택 false로 설정하면 슬래시 명령어로 직접 호출 불가. Claude가 내부적으로만 사용
allowed-tools 선택 이 스킬이 사용할 수 있는 도구 목록을 제한
model 선택 스킬 실행에 사용할 모델. 기본값은 현재 세션 모델
effort 선택 추론 노력 수준. low, normal, high 중 선택
context 선택 fork로 설정하면 현재 대화 맥락 없이 깨끗한 컨텍스트에서 실행
agent 선택 true로 설정하면 도구 사용이 가능한 에이전트 모드로 실행
paths 선택 특정 파일 경로 패턴과 매칭될 때만 스킬 활성화

실전 예시: spec-writer

---
name: spec-writer
version: 1.3.0
description: 시스템 요구사항 명세서(SRS)를 대화형 인터뷰를 통해 작성하는 스킬.
  IEEE 830 표준 기반으로 기능 요구사항, 비기능 요구사항(성능/보안/가용성), 인터페이스,
  제약조건을 체계적으로 정리하여 마크다운 파일로 저장한다.
  "요구사항 명세서 작성해줘", "SRS 만들어줘", "시스템 스펙 정리해줘" 같은 요청에 사용.
  "새 프로젝트 시작하는데 요구사항 정리 좀", "기능 명세 문서화해줘" 같은 간접적 요청에도
  반드시 사용한다. 단, 단순 기획서 작성, 회의록 정리, 코드 문서화(JSDoc/Javadoc),
  API 문서 자동생성(Swagger) 요청에는 사용하지 않는다.
---

description이 길다. 이는 의도적이다. Claude가 "언제 이 스킬을 써야 하는지"를 정확히 판단하려면, 긍정 예시(사용해야 할 표현)와 부정 예시(사용하지 말아야 할 경우) 모두가 필요하다. "시스템 스펙 정리해줘"와 "API 문서 자동생성(Swagger)"은 표면적으로 비슷해 보이지만 전혀 다른 스킬이 처리해야 한다. 부정 예시가 없으면 Claude는 혼동할 수 있다.

실전 예시: humanizer

---
name: humanizer
description: AI가 생성한 한국어/영어 텍스트에서 AI투(AI 냄새)를 제거하고 자연스러운
  사람 문체로 교정하는 스킬. "AI투 제거해줘", "사람처럼 다듬어줘", "humanize 해줘"
  같은 요청에 사용. "이거 AI가 쓴 티 나는데", "좀 자연스럽게 바꿔줘" 같은 간접적
  요청에도 반드시 사용한다. 단, 단순 맞춤법 교정이나 번역 요청에는 사용하지 않는다.
---

humanizer에는 version이 없다. 아직 버전 관리가 적용되지 않은 초기 스킬이다. 스킬을 개선할 계획이라면 처음부터 version: 1.0.0을 추가하는 것이 좋다. 버전 없이 운영하다 뒤늦게 추가하면 "이전에 쓰던 것과 지금이 같은 버전인지" 판단하기 어려워진다.

4. 스킬 본문 작성

기본 구성

frontmatter 아래에는 마크다운으로 자유롭게 작성한다. Claude는 이 내용을 시스템 프롬프트처럼 해석하여 실행한다. 분량 제한은 없지만, 길어질수록 Claude가 핵심을 놓칠 가능성이 높아진다. 긴 내용은 references/로 분리하고 SKILL.md는 간결하게 유지하는 것이 원칙이다.

좋은 스킬 본문은 네 가지를 포함한다.

  1. 핵심 원칙: 이 스킬이 왜 이렇게 동작하는지, 판단 기준이 무엇인지. 단순한 규칙 나열보다 "왜"를 설명하면 Claude가 예외 상황에서도 올바른 판단을 내릴 수 있다.
  2. 단계별 워크플로우: Claude가 순서대로 따라야 할 작업 흐름. ASCII 흐름도와 상세 단계 설명을 함께 쓰면 효과적이다.
  3. 예시: 전형적인 사용 시나리오. Claude가 스킬의 의도를 구체적으로 이해하도록 돕는다.
  4. 트러블슈팅: 자주 발생하는 예외 상황과 처리 방법. 모든 경우를 다 다룰 필요는 없고, 실제로 자주 마주치는 상황 3-5개면 충분하다.

인자 사용법

스킬은 사용자가 전달한 텍스트를 인자로 받을 수 있다.

변수 의미
$ARGUMENTS 슬래시 명령어 뒤에 오는 모든 텍스트
$0 스킬 이름
$1, $2, ... 공백으로 구분된 개별 인자

예를 들어 /code-analyzer src/auth 라고 호출하면 $ARGUMENTS는 src/auth가 되고 $1은 src/auth가 된다. /code-analyzer src/auth UserService.java처럼 여러 인자를 넘기면 $1은 src/auth, $2는 UserService.java가 된다.

인자 없이 자동 감지로만 호출되는 스킬이라면 $ARGUMENTS를 사용하지 않아도 된다. spec-writer나 humanizer처럼 호출 맥락 자체가 입력인 경우가 그렇다.

동적 컨텍스트 주입

스킬 본문 안에서 느낌표와 백틱을 조합한 문법으로 셸 명령어 실행 결과를 주입할 수 있다.

현재 디렉토리 구조: !`ls -la`
현재 날짜: !`date`
Git 브랜치: !`git branch --show-current`

스킬이 로드될 때 해당 명령어가 실행되고 결과가 인라인으로 삽입된다. 이를 통해 실행 환경에 따라 동적으로 달라지는 컨텍스트를 스킬에 반영할 수 있다. 날짜가 중요한 스킬(파일명에 날짜를 포함하는 경우)이나 현재 브랜치나 프로젝트 구조를 참고해야 하는 스킬에 유용하다.

핵심 원칙 섹션의 중요성

여러 스킬을 보면 공통적으로 "핵심 원칙" 섹션이 가장 먼저 등장한다. spec-writer의 핵심 원칙 중 하나는 이렇다.

사용자가 모호하게 답변하면 ("적당히", "알아서 해줘", "나중에 정하자") 그냥 넘기지 않는다. 구체적인 선택지를 제시하여 명확한 답변을 유도한다.

이것은 단순한 규칙이 아니라 판단 기준이다. Claude가 실제 인터뷰 중에 모호한 답변을 받았을 때 어떻게 행동해야 하는지 알려준다. "TBD로 기록하고 넘어가야 하나, 아니면 계속 질문해야 하나?" — 핵심 원칙이 이 판단을 내려준다.

performance-profiler의 핵심 원칙은 분석 관점을 명확히 한다.

추측이 아닌 코드 근거를 기반으로 판단한다. "느릴 수 있다"가 아니라 "N건 조회 시 N+1회 쿼리가 발생한다"처럼 구체적으로 설명한다.

이런 원칙이 없으면 Claude는 일반적인 성능 조언을 나열하는 데 그친다. 원칙이 있어야 스킬이 의도한 방향으로 일관되게 동작한다.

spec-writer의 본문 구조를 보면 워크플로우를 어떻게 표현하는지 알 수 있다.

## 상세 단계

### 1단계: 프로젝트 개요 인터뷰

시스템의 큰 그림을 파악한다. ...

ASCII 흐름도로 전체 구조를 한눈에 보여주고, 각 단계의 상세 지시는 별도 섹션으로 분리한다. Claude는 이 구조를 순서대로 따라간다. 흐름도 없이 상세 단계만 있으면 Claude가 전체 맥락을 파악하는 데 더 많은 처리가 필요하다.

5. references/ 디렉토리 활용

분리하는 이유

SKILL.md에 모든 내용을 넣으면 파일이 지나치게 길어진다. references/는 스킬 본문에서 참조할 보조 파일을 분리하는 공간이다. Claude가 스킬을 실행할 때 필요한 시점에 해당 파일을 읽어 참조한다.

performance-profiler는 다음처럼 카테고리별로 패턴 카탈로그를 분리했다.

references/
├── db-patterns.md        # N+1, 인덱스 누락 등 DB 쿼리 패턴
├── algorithm-patterns.md # O(n²), 비효율적 자료구조 패턴
├── memory-patterns.md    # 메모리 낭비 패턴
└── api-patterns.md       # API 응답 지연 패턴

SKILL.md에는 "상세 패턴 및 예시는 references/db-patterns.md 참조"라고만 쓰고, 실제 내용은 분리된 파일에 둔다. 스킬 본문은 간결하게, 세부 지식은 별도 파일로 관리하는 방식이다. 패턴 카탈로그가 바뀌어도 SKILL.md를 건드리지 않아도 된다는 장점도 있다. 단, 이 경우에도 references/ 파일이 변경되면 버전은 올려야 한다.

spec-writer는 두 종류의 보조 파일을 가진다.

references/
├── srs-template.md    # SRS 문서의 실제 형식 템플릿
└── interview-guide.md # 도메인별 맞춤 인터뷰 질문 목록

interview-guide.md에는 도메인별 특화 질문이 담겨 있다. 웹서비스인지, 모바일인지, 백오피스인지에 따라 물어야 할 내용이 다르다. 이 분기 로직을 SKILL.md에 모두 담으면 파일이 방대해진다. 별도 파일로 분리하면 SKILL.md는 "인터뷰 가이드를 참조하라"는 한 줄로 끝난다.

템플릿-지시문 일관성 규칙

이 프로젝트의 CLAUDE.md에는 다음 규칙이 명시되어 있다.

스킬이 references/ 디렉토리에 템플릿 파일을 가지고 있을 경우, SKILL.md의 지시문과 템플릿의 형식이 정확히 일치해야 한다.

이 규칙이 필요한 이유는 Claude가 두 파일을 모두 읽고 실행하기 때문이다. SKILL.md의 지시문이 "테이블은 4개 컬럼"이라고 하는데 srs-template.md가 "5개 컬럼"이면 Claude는 둘 중 어느 것을 따라야 할지 헷갈린다. 결과물이 매번 달라진다. 스킬을 팀에서 쓸 때 산출물의 형식이 사람마다 달라지는 문제가 생긴다.

spec-writer의 SKILL.md는 FR(기능 요구사항, Functional Requirement) 형식을 인라인으로 명시하고, references/srs-template.md도 동일한 형식을 사용한다.

#### FR-XXX: [기능 제목]

- **설명**: [기능이 무엇을 하는지]
- **선행 조건**: [이 기능이 실행되기 위한 조건]

**입력 데이터:**

| 필드명 | 타입 | 필수 여부 | 검증 규칙 | 설명 |
|--------|------|-----------|-----------|------|

**기본 흐름:**

1. [동작 1]
2. [동작 2]

**출력 데이터:**

| 필드명 | 타입 | 설명 |
|--------|------|------|

**예외 흐름:**

| 조건 | HTTP 상태 | 에러 코드 | 설명 |
|------|-----------|-----------|------|

- **후행 조건**: [기능 완료 후 시스템 상태]
- **우선순위**: 필수 / 권장 / 선택

이 형식은 SKILL.md와 srs-template.md 양쪽에 동일하게 정의되어 있다. 템플릿을 수정하면 지시문도 반드시 함께 수정해야 한다. 어느 한쪽만 바꾸면 산출물의 통일성이 깨진다. 규칙을 쉽게 기억하는 방법은 하나다 — 두 파일을 동시에 열어 같이 수정하는 것이다.

6. 버전 관리

시맨틱 버전 규칙

스킬은 내용이 변경될 때마다 버전을 올린다. 이 프로젝트의 CLAUDE.md에 정의된 규칙은 다음과 같다.

변경 유형 버전 변화 예시
patch 1.0.0 → 1.0.1 오타 수정, 문구 다듬기 등 동작에 영향 없는 변경
minor 1.0.0 → 1.1.0 기능 추가, 템플릿 구조 변경, 지시문 개선 등 동작에 영향 있는 변경
major 1.0.0 → 2.0.0 스킬의 목적이나 워크플로우가 근본적으로 바뀌는 변경

spec-writer의 현재 버전은 1.3.0이다. 커밋 이력을 보면 인터뷰 품질 향상 원칙 5가지 추가(minor), SRS 템플릿 대폭 개선(minor), 시스템 관점 다이어그램 예시 제거(patch) 순으로 변경이 누적되었다. 버전 번호만 봐도 이 스킬이 얼마나 성숙했는지 짐작할 수 있다.

버전 관리가 필요한 이유

버전 없이 스킬을 운영하면 두 가지 문제가 생긴다.

첫째, 언제 무엇이 바뀌었는지 추적하기 어렵다. "이번 SRS가 저번이랑 형식이 다른데?" 같은 상황이 생겼을 때 원인을 파악하기 어렵다. 버전 이력이 있으면 언제 템플릿이 바뀌었는지 바로 확인할 수 있다.

둘째, 팀에서 스킬을 공유할 때 혼선이 생긴다. "최신 버전 받았어요?"라는 말이 의미를 가지려면 버전이 있어야 한다. 버전이 없으면 파일을 직접 비교해야 한다.

SKILL.md의 변경과 references/의 변경 모두 버전 업 대상이다. references 파일만 고치고 SKILL.md 버전을 그대로 두면 버전이 실제 내용을 반영하지 못하게 된다.

7. 스킬 호출 제어

수동 호출만 허용

disable-model-invocation: true

이 옵션을 설정하면 Claude가 대화 맥락을 보고 자동으로 스킬을 실행하지 않는다. 사용자가 명시적으로 /skill-name이라고 입력해야만 실행된다.

민감한 작업이나 실수로 트리거되면 안 되는 스킬에 적합하다. 예를 들어 파일을 대량으로 수정하거나 외부 시스템에 데이터를 전송하는 스킬이라면 자동 감지보다 명시적 호출이 안전하다. "이 파일들 정리해줘"라는 말에 자동으로 대량 삭제 스킬이 실행되면 곤란하다.

Claude 내부 전용

user-invocable: false

이 옵션을 설정하면 사용자가 슬래시 명령어로 직접 호출할 수 없다. 다른 스킬이 내부적으로 호출하는 보조 스킬에 사용한다.

study-helper 스킬은 내부에서 /humanizer와 /external-context를 호출한다. 이 두 스킬을 사용자가 직접 호출하는 경우도 있으므로 user-invocable: false는 적용하지 않았지만, 순수하게 내부 전용 유틸리티라면 이 옵션으로 외부 노출을 차단할 수 있다. 사용자에게는 보이지 않고, 스킬 간 조합만 가능한 내부 모듈이 된다.

description이 자동 감지의 핵심

disable-model-invocation을 설정하지 않으면 Claude는 description을 읽고 현재 요청에 맞는 스킬을 자동으로 선택한다. 이 과정에서 description의 품질이 정확도를 결정한다.

잘 쓴 description의 특징은 세 가지다.

첫째, 스킬이 처리하는 작업을 한 문장으로 명확히 설명한다. 무엇을 입력으로 받고 무엇을 출력하는지가 드러나야 한다.

둘째, 사용자가 실제로 쓸 법한 표현을 구체적으로 나열한다. humanizer의 description을 보면 "AI투 제거해줘", "사람처럼 다듬어줘", "AI 냄새 빼줘", "humanize 해줘", "문체 교정해줘"처럼 다양한 표현을 열거하고 있다. Claude는 이 표현들과 사용자의 요청이 얼마나 유사한지 판단한다. 표현이 많을수록 다양한 방식으로 말하는 사용자를 폭넓게 커버할 수 있다.

셋째, 사용하지 말아야 할 경우를 명시한다. "단, 단순 맞춤법 교정이나 번역 요청에는 사용하지 않는다"처럼 부정 예시를 포함하면 오작동을 줄일 수 있다. 비슷해 보이지만 다른 스킬이 처리해야 할 요청을 걸러내는 역할을 한다. spec-writer는 "기획서 작성", "회의록 정리", "JSDoc", "Swagger"를 명시적으로 제외한다. 이 표현들이 없으면 Claude가 혼동하기 쉬운 경계 케이스들이다.

8. 핵심 정리

스킬을 처음 만들 때는 작게 시작하는 것이 좋다. humanizer처럼 SKILL.md 하나로 시작하고, 쓰다 보면서 references/가 필요한 시점이 오면 그때 분리한다. 처음부터 완벽한 구조를 만들려고 하면 오히려 시작이 늦어진다.

스킬을 만들기 전에 다음 체크리스트를 확인한다.

구조

  • SKILL.md가 있는가
  • 스킬 디렉토리 이름이 스킬 식별자와 일치하는가
  • 보조 파일이 필요한 경우 references/에 분리했는가

Frontmatter

  • name과 description이 있는가
  • description에 긍정 예시(언제 써야 하는지)와 부정 예시(언제 쓰지 말아야 하는지)가 모두 있는가
  • version: 1.0.0을 추가했는가
  • 자동 감지가 필요 없다면 disable-model-invocation: true를 추가했는가

본문

  • 핵심 원칙(왜 이렇게 동작하는지)이 명확한가
  • 단계별 워크플로우가 순서대로 기술되어 있는가
  • 전형적인 사용 예시(## Examples)가 있는가
  • 자주 발생하는 문제와 해결책(## Troubleshooting)이 있는가

일관성

  • references/에 템플릿이 있다면 SKILL.md의 지시문과 형식이 일치하는가
  • 변경 후 버전을 올렸는가
  • SKILL.md 변경 시 관련 references/ 파일도 함께 수정했는가 (반대도 마찬가지)

잘 만든 스킬은 한 번 작성해두면 반복 작업을 대신한다. spec-writer는 SRS 인터뷰 6단계 전 과정을 처리하고, performance-profiler는 Java 성능 분석 4개 카테고리를 체계적으로 점검한다. study-helper는 노션 페이지를 가져와 AI투 제거, 팩트체크, 검수 리포트 생성까지 자동으로 이어간다. 복잡한 작업일수록 스킬로 만들 때 효과가 크다.

문서 메타

난이도: 심화 | 선행 문서: Claude Code 시작하기

Claude Code의 동작을 가로채고 확장하는 Hooks의 이벤트, 타입, 설정 방법을 다룬다.

Hook이란?

Hook은 Claude Code의 특정 이벤트에 반응해 자동으로 실행되는 명령이다. Claude가 파일을 편집하거나 셸 명령을 실행하는 순간 가로채서, 포맷팅·검증·로깅 같은 부가 작업을 자동으로 처리할 수 있다.

Hook 없이도 Claude Code를 사용할 수 있다. 하지만 같은 작업을 반복적으로 지시해야 하는 상황이 생기면 Hook을 쓸 시점이다.

  • "파일 편집할 때마다 prettier 돌려줘" — 매번 말하는 대신 PostToolUse Hook으로 자동화한다.
  • "프로덕션 설정 파일은 절대 건드리지 마" — 매 세션마다 주의를 주는 대신 PreToolUse Hook으로 차단한다.
  • "작업 완료되면 슬랙에 알려줘" — 매번 지시하는 대신 Stop Hook으로 알림을 보낸다.

Hook은 settings.json의 hooks 키에 설정한다. 설정 파일 위치는 아래 Hook 설정 방법 섹션에서 다룬다.

Hook 이벤트

아래 타임라인에서 각 이벤트를 클릭하면 발생 시점·차단 가능 여부·활용 예시를 확인할 수 있습니다.

Claude Code는 다양한 이벤트에 Hook을 걸 수 있다. 아래는 주요 이벤트 목록이다. 전체 목록은 공식 문서를 참고한다.

이벤트 발생 시점 차단 가능 여부
SessionStart 세션 시작 또는 재개 시 아니오
PreToolUse 도구 실행 직전 예
PostToolUse 도구 실행 성공 후 아니오
PostToolUseFailure 도구 실행 실패 후 아니오
PermissionRequest 권한 확인 프롬프트 표시 시 예
UserPromptSubmit 사용자 메시지 제출 시 예
Notification Claude가 알림을 보낼 시점 아니오
Stop Claude 응답 완료 시 아니오
StopFailure Claude 응답 실패 시 아니오
SubagentStart 서브에이전트(하위 에이전트) 시작 시 아니오
SubagentStop 서브에이전트 종료 시 아니오
TaskCreated 태스크 생성 시 아니오
TaskCompleted 태스크 완료 시 아니오
PreCompact 대화 압축 직전 아니오
PostCompact 대화 압축 직후 아니오
SessionEnd 세션 종료 시 아니오

이 외에도 ConfigChange, CwdChanged, FileChanged, InstructionsLoaded, TeammateIdle, WorktreeCreate, WorktreeRemove, Elicitation, ElicitationResult 등의 이벤트가 있다. Hook 이벤트는 Claude Code 업데이트에 따라 추가될 수 있으므로 공식 문서를 기준으로 확인한다.

차단 가능한 이벤트(PreToolUse, PermissionRequest, UserPromptSubmit 등)에서는 Hook이 종료 코드 2를 반환하면 해당 작업이 실행되지 않는다. 차단이 불가능한 이벤트는 알림·로깅 용도로 사용하며, Hook의 반환값이 작업 실행 여부에 영향을 주지 않는다.

이벤트에 전달되는 컨텍스트

Hook이 실행될 때 Claude Code는 이벤트 관련 정보를 JSON 형태로 환경 변수 또는 표준 입력(stdin)으로 전달한다. PreToolUse와 PostToolUse의 경우 어떤 도구가 어떤 인자로 실행됐는지 확인할 수 있다.

{
  "tool_name": "Edit",
  "tool_input": {
    "file_path": "/src/app.ts",
    "old_string": "...",
    "new_string": "..."
  }
}

이 정보를 활용하면 특정 파일이나 특정 도구에만 반응하는 정교한 Hook을 작성할 수 있다.

Hook 타입

네 가지 Hook 타입을 카드로 정리했습니다. 카드를 클릭하면 각 타입의 예시 JSON 설정이 펼쳐집니다.

Hook에서 실행할 작업의 형태는 네 가지다.

command

셸 명령어를 직접 실행한다. 가장 일반적인 타입으로, 포맷터·린터·알림 스크립트 등을 처리할 때 사용한다.

{
  "type": "command",
  "command": "prettier --write $FILE_PATH"
}

prompt

Claude(Haiku 모델)에게 평가를 맡긴다. 자연어로 판단 기준을 정의하고, Claude가 해당 기준에 따라 허용 또는 차단 결정을 내린다.

{
  "type": "prompt",
  "prompt": "이 파일 편집이 보안에 영향을 줄 수 있는지 확인해라. 영향이 있다면 차단하라."
}

단순한 규칙은 command 타입으로, 맥락에 따른 판단이 필요한 경우에는 prompt 타입을 사용한다.

agent

서브에이전트(하위 에이전트)를 별도로 실행해 검증 작업을 맡긴다. prompt 타입보다 더 복잡한 도구 사용이 필요할 때 적합하다.

{
  "type": "agent",
  "agent": "security-reviewer",
  "prompt": "변경된 파일에서 SQL 인젝션 취약점을 검토하라."
}

http

HTTP 엔드포인트를 호출한다. 외부 서비스와 연동하거나 웹훅(webhook, 이벤트 기반 HTTP 콜백)을 전송할 때 사용한다.

{
  "type": "http",
  "url": "https://hooks.example.com/claude-event",
  "method": "POST",
  "headers": {
    "Authorization": "Bearer $WEBHOOK_TOKEN"
  }
}

Hook 설정 방법

Hook은 settings.json의 hooks 키 아래에 이벤트별로 배열로 작성한다.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "prettier --write $TOOL_INPUT_FILE_PATH"
          }
        ]
      }
    ]
  }
}

matcher 필드

matcher는 정규식으로 대상 도구를 필터링한다. PreToolUse와 PostToolUse에서 유용하다. 설정하지 않으면 해당 이벤트의 모든 도구 호출에 반응한다.

"matcher": "Edit|Write"        // Edit 또는 Write 도구에만 반응
"matcher": "Bash"              // Bash 도구에만 반응
"matcher": "Edit|Write|Bash"   // 세 가지 모두에 반응

설정 파일 위치

Hook도 settings.json에 저장한다. 파일 위치에 따라 적용 범위가 달라진다.

파일 위치 적용 범위
글로벌 설정 ~/.claude/settings.json 모든 프로젝트
프로젝트 설정 .claude/settings.json 해당 프로젝트 (팀 공유)
로컬 설정 .claude/settings.local.json 해당 프로젝트 (개인 전용)

보안 검사처럼 팀 전체에 강제할 Hook은 프로젝트 설정에, 데스크톱 알림처럼 개인 환경에 맞는 Hook은 로컬 설정에 둔다.

실전 활용 패턴

패턴 1: 파일 편집 후 자동 포맷팅

파일을 편집할 때마다 prettier를 자동으로 실행한다. 포맷팅을 직접 지시하지 않아도 된다.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npx prettier --write \"$TOOL_INPUT_FILE_PATH\" 2>/dev/null || true"
          }
        ]
      }
    ]
  }
}

2>/dev/null || true를 붙이는 이유는 prettier가 지원하지 않는 파일 형식을 만났을 때 오류로 인해 작업이 중단되지 않도록 하기 위해서다.

패턴 2: 보호된 파일 수정 방지

특정 파일에 대한 편집을 사전에 차단한다. 프로덕션 설정 파일이나 보안 관련 파일을 실수로 수정하는 것을 막는 데 효과적이다.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "python3 -c \"\nimport json, sys\ndata = json.load(sys.stdin)\npath = data.get('tool_input', {}).get('file_path', '')\nprotected = ['.env', '.env.production', 'secrets.yaml']\nif any(p in path for p in protected):\n    print(f'차단됨: {path}는 보호된 파일입니다.')\n    sys.exit(2)\n\""
          }
        ]
      }
    ]
  }
}

종료 코드 2를 반환하면 Claude Code가 해당 편집을 실행하지 않고 차단 메시지를 표시한다.

패턴 3: 데스크톱 알림

Claude가 작업을 완료하거나 사람의 입력을 기다릴 때 데스크톱 알림을 보낸다. 긴 작업을 맡겨두고 다른 일을 할 때 유용하다.

macOS:

{
  "hooks": {
    "Notification": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude Code가 응답을 기다리고 있습니다.\" with title \"Claude Code\"'"
          }
        ]
      }
    ]
  }
}

Windows:

{
  "hooks": {
    "Notification": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "powershell -Command \"[System.Windows.Forms.MessageBox]::Show('Claude Code가 응답을 기다리고 있습니다.', 'Claude Code')\""
          }
        ]
      }
    ]
  }
}

패턴 4: 권한 자동 승인

특정 도구나 명령에 대해 매번 확인 없이 자동으로 허용한다. 반복적인 승인 클릭을 줄일 수 있다.

{
  "hooks": {
    "PermissionRequest": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 -c \"\nimport json, sys\ndata = json.load(sys.stdin)\ncmd = data.get('tool_input', {}).get('command', '')\nsafe_prefixes = ['git status', 'git log', 'git diff', 'npm test', 'npx jest']\nif any(cmd.startswith(p) for p in safe_prefixes):\n    sys.exit(0)\nelse:\n    sys.exit(1)\n\""
          }
        ]
      }
    ]
  }
}

종료 코드 0은 허용, 1은 기본 동작(사용자에게 확인 요청)으로 처리된다.

종료 코드

Hook은 종료 코드로 다음 동작을 제어한다.

종료 코드 의미
0 정상 처리. 작업을 진행한다.
2 작업 차단. PreToolUse와 PermissionRequest에서만 효과가 있다.
그 외 Hook 실행 실패로 처리. 작업은 진행된다.

stdout으로 메시지 전달

Hook이 표준 출력(stdout)으로 내보내는 텍스트는 Claude Code가 읽어 컨텍스트에 포함한다. 차단 이유나 추가 정보를 전달할 때 활용한다.

#!/bin/bash
FILE_PATH="$1"

if [[ "$FILE_PATH" == *".env"* ]]; then
    echo "이 파일은 민감한 환경 변수를 포함합니다. 수정이 차단됩니다."
    exit 2
fi

Claude는 이 메시지를 읽고 왜 작업이 차단됐는지 이해하며, 필요하면 대안을 제시한다.

주의사항

무한 루프 방지

Hook이 다른 Hook을 트리거하는 상황을 조심해야 한다. 예를 들어 PostToolUse에서 파일을 수정하는 Hook을 걸면, 그 수정이 다시 PostToolUse를 발생시켜 무한 루프가 생길 수 있다.

Claude Code는 Hook이 재귀적으로 실행되지 않도록 내부적으로 보호 장치를 두고 있지만, 외부 스크립트가 파일을 직접 쓰는 경우에는 이 보호 장치가 작동하지 않는다. Hook 스크립트가 편집 도구를 호출하지 않고 OS 수준에서 직접 파일을 쓰도록 작성하는 편이 안전하다.

성능 영향

Hook은 매 도구 호출마다 실행된다. 무거운 작업을 Hook에 넣으면 Claude의 응답이 느려진다. 다음 원칙을 지킨다.

  • 포맷터처럼 빠른 작업만 동기 Hook으로 처리한다.
  • 30초 이상 걸리는 작업은 백그라운드(background)로 실행한다.
  • 무거운 테스트 스위트 전체를 Hook으로 돌리는 것은 피한다. 관련 파일만 선별해 실행한다.

디버깅

현재 세션에 어떤 Hook이 등록됐는지 확인하려면 세션 내에서 슬래시 명령을 사용한다.

/hooks

Hook이 기대한 대로 동작하지 않을 때는 Hook 스크립트를 터미널에서 직접 실행해 동작을 확인한다. stdin으로 예상 JSON을 넘겨 테스트하면 문제를 빠르게 파악할 수 있다.

echo '{"tool_name":"Edit","tool_input":{"file_path":"/src/app.ts"}}' | bash my-hook.sh

핵심 정리

Hook 설정 체크리스트

  • 이벤트가 올바른가? (PreToolUse vs PostToolUse)
  • matcher 정규식이 의도한 도구만 선택하는가?
  • 차단이 필요한 경우 종료 코드 2를 반환하는가?
  • Hook 스크립트 자체가 충분히 빠른가?
  • 무한 루프 가능성이 없는가?
  • 설정 파일 위치가 적용 범위(글로벌/프로젝트/로컬)와 맞는가?
  • /hooks 명령으로 등록 여부를 확인했는가?

Hook vs 스킬: 언제 무엇을 쓸 것인가

Hook과 스킬(Skill)은 모두 Claude Code의 동작을 확장하지만 쓰임새가 다르다.

Hook을 써야 하는 경우:

  • "파일을 편집할 때마다 X를 자동으로 실행해야 한다"처럼 특정 이벤트에 반드시 반응해야 할 때
  • 사람의 지시 없이 자동으로 실행되어야 할 때
  • 특정 작업을 차단하거나 권한을 자동 승인해야 할 때

스킬을 써야 하는 경우:

  • 사용자가 슬래시 명령(/스킬이름)으로 직접 실행하는 워크플로우를 만들 때
  • Claude에게 복잡한 작업 절차나 출력 형식을 주입해야 할 때
  • 자동 실행이 아닌 온디맨드(on-demand, 요청 시 실행) 방식으로 동작해야 할 때

요약하면, Hook은 "이벤트가 발생할 때마다 자동으로"이고 스킬은 "내가 원할 때 꺼내 쓰는 워크플로우"다.

Chapter 05

MCP 서버 연동

문서 메타

난이도: 중급~심화 | 선행 문서: Claude Code 시작하기

Model Context Protocol(MCP)의 개념과 Claude Code에서 외부 서비스를 연동하는 방법을 다룬다.

MCP란?

MCP(Model Context Protocol, 모델 컨텍스트 프로토콜)는 Claude가 외부 서비스와 상호작용하는 방식을 표준화한 오픈 프로토콜이다. Anthropic이 설계하고 공개한 이 프로토콜은 Claude가 웹 브라우저, 데이터베이스, 협업 도구, 버전 관리 시스템 등 다양한 외부 시스템과 일관된 방식으로 통신할 수 있도록 한다.

Claude Code는 기본적으로 파일 읽기, 셸 명령 실행, git 작업 등 로컬 환경에서의 작업을 수행한다. MCP를 연동하면 Claude Code가 할 수 있는 일의 범위가 외부 서비스로 확장된다. GitHub에서 이슈를 가져오거나, PostgreSQL 데이터베이스에 쿼리를 실행하거나, Notion 페이지를 생성하는 작업을 Claude Code 세션 안에서 직접 처리할 수 있다.

MCP 서버가 제공하는 것

MCP 서버는 세 가지 요소를 Claude에게 제공한다.

  • 도구(tools): Claude가 직접 호출할 수 있는 함수다. GitHub의 이슈 생성, 데이터베이스 쿼리 실행, 브라우저 탐색 등이 이에 해당한다.
  • 리소스(resources): Claude가 읽을 수 있는 데이터 소스다. 파일, URL, 데이터베이스 레코드처럼 컨텍스트에 포함할 수 있는 정보다.
  • 프롬프트(prompts): 특정 작업에 최적화된 프롬프트 템플릿이다. MCP 서버가 자주 쓰는 작업 패턴을 미리 정의해 제공한다.

실제 사용에서는 도구가 가장 자주 쓰인다. MCP 서버를 연동하면 Claude가 해당 서버의 도구를 자연어 요청에 따라 자동으로 호출한다.

MCP 서버 추가 방법

CLI로 추가

가장 빠른 방법이다. 터미널에서 아래 형식으로 명령을 실행한다.

claude mcp add <서버-이름> -- <실행-명령> [인자...]

예를 들어 GitHub MCP 서버를 추가하려면 다음과 같이 입력한다.

claude mcp add github -- npx @anthropic-ai/github-mcp

CLI로 추가하면 설정이 ~/.claude/.mcp.json(글로벌) 또는 .mcp.json(프로젝트)에 자동으로 기록된다. 범위를 지정하려면 -s 플래그를 사용한다.

claude mcp add --scope local github -- npx @anthropic-ai/github-mcp   # 현재 프로젝트에만 적용
claude mcp add --scope user github -- npx @anthropic-ai/github-mcp    # 모든 프로젝트에 적용

설정 파일로 추가

.mcp.json 파일을 직접 작성해 서버를 등록할 수 있다. 팀 전체에 동일한 MCP 설정을 배포하거나, 여러 서버를 한 번에 구성할 때 유용하다.

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["@anthropic-ai/github-mcp"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "postgres": {
      "command": "npx",
      "args": ["@modelcontextprotocol/server-postgres"],
      "env": {
        "DATABASE_URL": "${DATABASE_URL}"
      }
    }
  }
}

env 필드의 ${변수명} 형식은 실행 환경의 환경 변수를 참조한다. 민감한 값을 파일에 직접 넣지 않고 환경 변수로 관리할 수 있다.

설정 범위

MCP 서버 설정은 두 범위로 나뉜다.

글로벌 설정

~/.claude.json

모든 프로젝트에서 공통으로 사용할 MCP 서버를 등록한다. 개인 개발 환경에서 자주 쓰는 서버(GitHub, Notion 등)는 글로벌로 등록해두면 프로젝트마다 반복 설정할 필요가 없다.

프로젝트 설정

.mcp.json         # 프로젝트 루트
.claude/.mcp.json # .claude 디렉토리 안

특정 프로젝트에서만 사용할 MCP 서버를 등록한다. 이 파일은 git에 커밋해 팀과 공유한다. 프로젝트에 필요한 데이터베이스 서버나 특수 도구를 여기에 정의한다.

환경 변수로 민감한 값 관리

API 토큰, 데이터베이스 연결 문자열 같은 값은 .mcp.json에 직접 넣지 않는다. 대신 환경 변수로 관리하고 파일에서는 참조만 한다.

운영 체제의 환경 변수로 설정하는 방법은 다음과 같다.

# macOS / Linux (.bashrc 또는 .zshrc에 추가)
export GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxx
export DATABASE_URL=postgresql://user:pass@localhost:5432/mydb

# Windows (PowerShell 프로필에 추가)
$env:GITHUB_TOKEN = "ghp_xxxxxxxxxxxxxxxx"
$env:DATABASE_URL = "postgresql://user:pass@localhost:5432/mydb"

주요 MCP 서버 소개

GitHub MCP

GitHub의 이슈, PR(Pull Request, 풀 리퀘스트), 코드 리뷰, 리포지토리 관리를 Claude에서 처리할 수 있다.

claude mcp add github -- npx @anthropic-ai/github-mcp

환경 변수 GITHUB_TOKEN에 GitHub Personal Access Token(개인 접근 토큰)을 설정해야 한다. 주요 도구는 다음과 같다.

  • create_issue: 이슈 생성
  • list_pull_requests: PR 목록 조회
  • create_review: PR에 리뷰 추가
  • get_file_contents: 리포지토리 파일 내용 조회

Claude Code 세션에서 "이 버그를 이슈로 등록해줘"라고 요청하면 GitHub MCP가 자동으로 이슈를 생성한다.

Playwright MCP

Playwright(플레이라이트)는 웹 브라우저 자동화 라이브러리다. Playwright MCP를 연동하면 Claude가 브라우저를 직접 제어해 웹 페이지를 탐색하고 테스트를 실행할 수 있다.

claude mcp add playwright -- npx @playwright/mcp@latest

주요 도구는 다음과 같다.

  • browser_navigate: URL로 이동
  • browser_take_screenshot: 현재 화면 캡처
  • browser_fill_form: 폼 입력
  • browser_click: 요소 클릭
  • browser_snapshot: 접근성 트리(Accessibility Tree) 스냅샷 캡처

"로그인 페이지에서 유효하지 않은 이메일을 입력했을 때 어떤 오류 메시지가 나오는지 확인해줘"와 같은 요청을 Claude Code에서 직접 처리할 수 있다.

Notion MCP

Notion(노션) 워크스페이스의 페이지와 데이터베이스를 Claude에서 읽고 편집할 수 있다.

claude mcp add notion -- npx @anthropic-ai/notion-mcp

환경 변수 NOTION_API_KEY에 Notion Integration Token(통합 토큰)을 설정해야 한다. 주요 도구는 다음과 같다.

  • search_pages: 페이지 검색
  • get_page: 특정 페이지 내용 조회
  • create_page: 새 페이지 생성
  • update_page: 페이지 내용 수정
  • query_database: 데이터베이스 레코드 조회

회의록 정리, 작업 현황 문서 업데이트, 팀 위키 작성 등의 작업을 Claude Code 세션에서 처리할 수 있다.

Context7 MCP

Context7(컨텍스트세븐)은 라이브러리의 공식 문서를 실시간으로 가져오는 MCP 서버다. Claude의 학습 데이터 기준일 이후 변경된 API나 새 버전의 문서를 정확하게 참조할 때 유용하다.

claude mcp add context7 -- npx @context7/mcp

사용 패턴은 두 단계로 이뤄진다.

  1. resolve-library-id: 라이브러리 이름으로 고유 ID를 조회한다.
  2. query-docs: 조회한 ID를 사용해 특정 주제의 문서를 가져온다.

예를 들어 "Next.js App Router에서 서버 컴포넌트를 사용하는 방법"을 물으면 Context7이 Next.js 공식 문서에서 최신 정보를 가져와 답변에 반영한다. 빠르게 업데이트되는 프레임워크를 다룰 때 특히 효과적이다.

PostgreSQL MCP

PostgreSQL(포스트그레스큐엘) 데이터베이스에 쿼리를 실행하고 스키마를 탐색할 수 있다.

claude mcp add postgres -- npx @modelcontextprotocol/server-postgres

환경 변수 DATABASE_URL에 연결 문자열을 설정한다. 주요 도구는 다음과 같다.

  • query: SQL 쿼리 실행
  • list_tables: 테이블 목록 조회
  • describe_table: 테이블 스키마 확인

"users 테이블에서 지난 30일 동안 로그인하지 않은 계정 수를 알려줘"처럼 자연어로 데이터를 요청하면 Claude가 SQL을 작성하고 결과를 반환한다.

MCP 서버 관리

등록된 MCP 서버는 다음 명령으로 관리한다.

# 등록된 서버 목록 확인
claude mcp list

# 특정 서버 상세 정보 확인
claude mcp get github

# 서버 제거
claude mcp remove github

서버 상태 확인 및 디버깅

MCP 서버가 정상적으로 연결되지 않을 때는 Claude Code 세션 안에서 /mcp 명령을 실행한다.

/mcp

연결된 서버 목록과 각 서버의 상태(연결됨 / 오류)를 표시한다. 오류가 있는 서버는 실행 명령과 환경 변수 설정을 다시 확인한다.

디버깅이 필요하면 --mcp-debug 플래그를 사용해 Claude Code를 실행한다.

claude --mcp-debug

MCP 서버와의 통신 로그를 출력해 어떤 요청을 보내고 어떤 응답을 받았는지 추적할 수 있다.

보안 고려 사항

환경 변수로 토큰과 API 키 관리

.mcp.json 파일에 API 키나 토큰을 직접 입력하면 git에 커밋될 때 유출 위험이 생긴다. 반드시 환경 변수로 관리하고 파일에서는 ${변수명} 형식으로 참조한다.

프로젝트의 .gitignore에 민감한 값이 담긴 파일(.env, .env.local 등)이 포함되어 있는지 확인한다.

MCP 서버의 권한 범위 이해

MCP 서버는 등록한 도구를 통해 외부 서비스에 실제 작업을 수행한다. GitHub MCP가 PR을 생성하거나 이슈를 닫는 것은 실제 리포지토리에 적용된다. 연동하기 전에 다음을 확인한다.

  • 해당 서버가 어떤 도구를 제공하는지
  • 각 도구가 읽기 전용인지 쓰기 작업을 포함하는지
  • 사용하는 토큰의 권한 범위가 최소한으로 설정되어 있는지

GitHub Personal Access Token을 발급할 때 리포지토리 읽기만 필요하다면 쓰기 권한은 부여하지 않는다. 최소 권한 원칙(Principle of Least Privilege)을 적용한다.

출처를 알 수 없는 MCP 서버 주의

공식 Anthropic MCP 서버와 잘 알려진 커뮤니티 서버는 대체로 안전하다. 그러나 출처를 확인하기 어려운 MCP 서버를 연동할 때는 소스 코드를 검토하거나 샌드박스(격리된 환경) 환경에서 먼저 테스트한다.

커스텀 MCP 서버 만들기

자주 사용하는 내부 API나 사내 시스템을 MCP로 래핑하면 Claude Code에서 직접 연동할 수 있다. MCP 서버는 Python(FastMCP 라이브러리)이나 Node.js(공식 MCP SDK)로 구현한다.

Python(FastMCP)으로 구현하는 예시

from fastmcp import FastMCP

mcp = FastMCP("my-internal-api")

@mcp.tool()
def get_deployment_status(service_name: str) -> dict:
    """배포 상태를 조회한다."""
    # 내부 API 호출 로직
    return {"service": service_name, "status": "running", "version": "1.2.3"}

if __name__ == "__main__":
    mcp.run()

Node.js(MCP SDK)로 구현하는 예시

import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";

const server = new Server({ name: "my-internal-api", version: "1.0.0" });

server.setRequestHandler("tools/list", async () => ({
  tools: [
    {
      name: "get_deployment_status",
      description: "배포 상태를 조회한다",
      inputSchema: {
        type: "object",
        properties: { service_name: { type: "string" } },
        required: ["service_name"],
      },
    },
  ],
}));

const transport = new StdioServerTransport();
await server.connect(transport);

MCP 도입 체크리스트

  • 연동할 서비스의 API 토큰을 발급하고 환경 변수로 설정했는가?
  • .mcp.json에 민감한 값이 직접 입력되어 있지 않은가?
  • 글로벌 설정과 프로젝트 설정의 범위를 올바르게 구분했는가?
  • 팀과 공유할 프로젝트 .mcp.json을 git에 커밋했는가?
  • /mcp 명령으로 서버 연결 상태를 확인했는가?
  • 사용하는 토큰에 최소 필요 권한만 부여했는가?

어떤 MCP 서버를 먼저 설정할 것인가

MCP 서버를 처음 도입할 때 모든 서버를 한꺼번에 설정하려 하면 관리가 복잡해진다. 아래 기준으로 우선순위를 정한다.

1순위 — GitHub MCP: 코드 작업과 가장 밀접하다. 이슈 확인, PR 리뷰, 브랜치 관리 등을 Claude Code 세션에서 처리할 수 있다. 대부분의 개발자에게 즉각적인 생산성 향상을 제공한다.

2순위 — Context7 MCP: 외부 라이브러리 문서를 실시간으로 참조한다. 새 프레임워크를 학습하거나 빠르게 변하는 API를 다룰 때 Claude의 답변 정확도가 눈에 띄게 높아진다.

3순위 — Playwright MCP: 프론트엔드 개발이나 웹 테스트 자동화 작업이 많다면 초기부터 도입할 가치가 있다. 수동으로 브라우저를 확인해야 했던 작업을 Claude에게 위임할 수 있다.

4순위 — 데이터베이스 MCP: 백엔드 개발이나 데이터 분석 업무가 많다면 PostgreSQL MCP나 유사한 서버를 추가한다. 단, 프로덕션 데이터베이스에 직접 연결하는 것은 위험하다. 개발 또는 읽기 전용 복제본에 연결하는 것을 권장한다.

5순위 — Notion MCP 등 협업 도구: 문서화나 프로젝트 관리 작업이 많을 때 추가한다. 코딩 작업보다는 관리 업무에 직접적인 영향을 준다.

문서 메타

난이도: 중급~심화 | 선행 문서: Claude Code 시작하기

Git 연동, 멀티에이전트 작업, 컨텍스트 관리 등 Claude Code를 실무에서 활용하는 패턴을 다룬다.

Git 연동

Claude Code는 git 작업을 자연어로 처리할 수 있다. 변경 사항 분석부터 PR(Pull Request, 풀 리퀘스트) 생성까지 터미널을 벗어나지 않고 진행된다.

커밋 메시지 자동 생성

claude commit

스테이징된 변경 사항을 분석해 Conventional Commits(컨벤셔널 커밋) 형식의 메시지를 작성하고 커밋한다. 변경된 파일의 목적과 범위를 파악해 feat:, fix:, refactor: 같은 타입을 자동으로 선택한다.

세션 안에서도 같은 작업을 요청할 수 있다.

변경사항 분석하고 적절한 커밋 메시지로 커밋해줘

CLAUDE.md에 커밋 메시지 형식을 명시해 두면 Claude가 팀 컨벤션을 따른다. 예를 들어 "커밋 메시지는 한국어로 작성한다"고 적어두면 매 세션에서 별도로 지시하지 않아도 된다.

PR 생성

변경사항 커밋하고 PR 열어줘

Claude가 스테이징된 변경 사항을 커밋하고, 브랜치를 원격 저장소에 푸시한 뒤, PR 제목과 본문을 작성해 생성한다. PR 본문에는 변경의 목적, 주요 변경 파일, 테스트 방법이 자동으로 포함된다.

gh CLI(GitHub CLI)가 설치되어 있어야 이 기능을 사용할 수 있다. gh auth login으로 먼저 인증한다.

코드 리뷰 요청 및 피드백 반영

PR을 생성하고 리뷰를 받은 뒤 피드백을 반영하는 과정도 Claude와 함께 진행할 수 있다.

PR #42 리뷰 코멘트 가져와서 피드백 반영해줘

Claude가 PR의 리뷰 코멘트를 읽고 각 항목을 코드에 반영한다. 반영이 완료되면 변경 사항을 정리해 알려준다.

브랜치 관리

feature/payment 브랜치 만들고 거기서 작업 시작해줘

main 브랜치와 현재 브랜치의 차이점을 요약해줘

브랜치 생성, 전환, 비교 등 일상적인 git 작업을 자연어로 처리한다. 복잡한 git 명령을 외울 필요 없이 의도를 전달하면 된다.

Plan Mode 활용

Plan Mode(계획 모드)는 Claude가 실제 변경을 가하지 않고 읽기 전용으로 코드베이스를 탐색하며 작업 계획을 세우는 모드다. 대규모 작업을 시작하기 전에 Claude가 어떤 파일을 어떻게 수정할지 먼저 파악하는 용도로 사용한다.

Plan Mode 진입

세션 중 Shift+Tab을 눌러 모드를 순환한다. default, acceptEdits, plan, 그리고 사용자가 활성화한 모드(예: auto, bypassPermissions)를 순서대로 전환한다. 현재 활성 모드는 프롬프트 옆에 표시된다.

읽기 전용 탐색에서 구현으로

Plan Mode의 전형적인 사용 패턴은 다음과 같다.

  1. Plan Mode 진입
  2. "인증 모듈을 OAuth 2.0으로 교체하려면 어떤 파일을 수정해야 해?"와 같이 탐색 요청
  3. Claude가 관련 파일을 읽고 변경 범위를 분석해 계획을 제시
  4. 계획 검토 후 Shift+Tab으로 default 모드로 전환
  5. "계획대로 구현해줘"

계획 단계에서 실수를 발견하면 구현 전에 방향을 수정할 수 있다. 잘못된 파일을 대규모로 수정한 뒤 되돌리는 것보다 비용이 훨씬 적다.

계획을 텍스트 에디터에서 편집

Plan Mode에서 Claude가 계획을 제시한 뒤 Ctrl+G를 누르면 현재 계획을 텍스트 에디터에서 열 수 있다. 에디터에서 직접 계획을 수정하거나 보완한 뒤 저장하면 Claude가 수정된 계획을 기반으로 구현을 진행한다.

자동화 환경에서 Plan Mode를 강제하려면 다음 플래그를 사용한다.

claude --permission-mode plan "인증 모듈 리팩토링 계획 세워줘"

멀티 세션과 워크트리

독립적인 작업을 동시에 진행해야 할 때 멀티 세션과 git worktree(워크트리)를 활용한다.

여러 터미널에서 독립 세션 실행

Claude Code 세션은 서로 독립적이다. 터미널 탭을 추가로 열고 claude를 실행하면 별개의 컨텍스트를 가진 새 세션이 시작된다.

# 터미널 1: 프론트엔드 작업
claude
> 결제 UI 컴포넌트 만들어줘

# 터미널 2: 백엔드 작업
claude
> 결제 API 엔드포인트 구현해줘

두 세션은 컨텍스트를 공유하지 않는다. 한쪽의 긴 작업이 다른 쪽 세션의 응답 속도나 컨텍스트에 영향을 주지 않는다.

워크트리로 브랜치 격리

git worktree는 하나의 로컬 저장소에서 여러 브랜치를 동시에 체크아웃하는 기능이다. Claude Code와 함께 사용하면 각 브랜치를 완전히 격리된 디렉토리에서 독립적으로 작업할 수 있다.

# feature/auth 브랜치를 별도 디렉토리에 체크아웃
git worktree add ../my-project-auth feature/auth

# 해당 디렉토리에서 Claude Code 세션 실행
cd ../my-project-auth
claude

claude --worktree 플래그를 사용하면 워크트리 생성과 세션 시작을 한 번에 처리한다.

claude --worktree feature/auth

병렬 개발의 장점

워크트리 기반 병렬 세션의 실질적인 이점은 세 가지다.

첫째, 컨텍스트가 완전히 분리된다. 한 세션에서 대규모 리팩토링을 진행하더라도 다른 세션의 버그 수정 작업에 영향을 주지 않는다.

둘째, 브랜치 전환 비용이 없다. git stash나 git checkout으로 작업 중인 변경을 임시 저장하고 전환할 필요가 없다.

셋째, 각 세션이 독립된 컨텍스트를 유지하므로 응답이 빠르다. 컨텍스트가 한 작업에 집중되어 있어 불필요한 정보로 인한 혼선이 줄어든다.

컨텍스트 관리

컨텍스트 관리는 Claude Code를 실무에서 효과적으로 사용하기 위한 가장 중요한 기술이다. 컨텍스트 창이 가득 차면 Claude의 응답 품질이 눈에 띄게 떨어진다.

컨텍스트 가득 참 신호

다음 증상이 나타나면 컨텍스트가 한계에 달했다는 신호다.

  • 응답이 짧아지거나 요청의 일부만 처리된다
  • 이전 대화에서 결정한 사항을 반복 확인하거나 잊는다
  • 수정 중인 파일과 관련 없는 파일을 참조한다
  • "이전에 말씀하신 것처럼..." 같은 표현과 함께 맥락 없는 내용을 언급한다

/clear: 전체 리셋

/clear

현재 대화 컨텍스트를 전부 삭제하고 빈 상태로 시작한다. 작업 중인 파일의 변경 사항은 디스크에 그대로 남는다. 새로운 작업을 시작하거나 대화가 산만해졌을 때 사용한다.

/compact: 대화 압축

/compact

전체 대화를 요약해 컨텍스트를 압축한다. 현재 작업의 핵심 내용은 유지하면서 불필요한 중간 과정을 제거한다. 작업을 완전히 버리지 않고 계속 이어가야 할 때 유용하다.

특정 내용을 압축 요약에 반드시 포함하도록 지시할 수 있다.

/compact 현재 진행 중인 인증 모듈 리팩토링 계획과 이미 수정한 파일 목록을 반드시 포함해

Esc+Esc로 부분 요약

메시지를 보내기 전 Esc를 두 번 누르면 "Summarize" 옵션이 나타난다. 현재까지의 대화를 요약한 뒤 새 메시지를 이어서 보낸다. /compact와 달리 요약 범위를 더 세밀하게 조절할 수 있다.

/btw: 컨텍스트를 소비하지 않는 사이드 질문

/btw 이 라이브러리가 ESM을 지원하나?

/btw 명령은 현재 작업 컨텍스트에 영향을 주지 않는 가벼운 질문을 처리한다. 주 작업의 흐름을 방해하지 않고 간단한 정보를 조회할 때 사용한다. /btw로 주고받은 내용은 이후 대화의 컨텍스트에 포함되지 않는다.

큰 파일은 필요한 부분만 요청

파일 전체를 읽도록 요청하면 컨텍스트를 빠르게 소진한다. 필요한 함수나 섹션만 명시적으로 지정한다.

# 비효율적
payment.service.ts 파일 읽어줘

# 효율적
payment.service.ts에서 processRefund 함수만 읽어줘
payment.service.ts의 150-200번째 줄만 읽어줘

Claude가 자동으로 전체 파일을 읽으려는 경향이 있다면 "필요한 함수만 읽고 전체 파일은 읽지 마"라는 지시를 CLAUDE.md에 추가한다.

서브에이전트 활용

서브에이전트(Sub-agent)는 Claude Code가 복잡한 작업을 처리할 때 자동으로 생성하는 독립 실행 단위다. 탐색, 계획, 구현을 각기 다른 에이전트에 분리해 메인 컨텍스트를 보호하는 방식으로 동작한다.

자동 서브에이전트 생성

Claude Code는 다음 상황에서 자동으로 서브에이전트를 생성한다.

  • 여러 디렉토리를 동시에 탐색해야 하는 경우
  • 독립적인 하위 작업이 병렬로 처리 가능한 경우
  • 메인 컨텍스트를 소비하지 않고 특정 파일을 탐색해야 하는 경우

명시적으로 서브에이전트 사용을 요청할 수도 있다.

서브에이전트를 사용해서 src/ 디렉토리 전체 구조를 탐색하고 보고해줘

Ctrl+T: 작업 목록 확인

Ctrl+T를 누르면 현재 실행 중인 작업과 서브에이전트의 상태를 확인할 수 있다. 각 서브에이전트가 어떤 작업을 처리 중인지, 완료 여부가 표시된다.

Ctrl+B: 백그라운드 전환

시간이 오래 걸리는 작업이 진행 중일 때 Ctrl+B를 누르면 해당 작업을 백그라운드로 전환하고 새로운 요청을 입력할 수 있다. 백그라운드 작업이 완료되면 알림이 표시된다.

검증 자동화

Claude Code는 코드 작성과 검증을 하나의 흐름으로 처리할 수 있다. 테스트 실행, 스크린샷 비교, CI/CD(Continuous Integration/Continuous Deployment, 지속적 통합·배포) 연동까지 모두 세션 안에서 다룬다.

테스트-커밋 통합 패턴

테스트 작성하고 실행해서 통과하면 커밋해줘

Claude가 구현 코드에 대한 테스트를 작성하고, 테스트를 실행한 뒤, 모든 테스트가 통과하면 커밋한다. 실패한 테스트가 있으면 원인을 분석하고 코드를 수정한 뒤 다시 실행한다. 사람이 개입하지 않아도 이 과정이 자동으로 반복된다.

스크린샷 비교를 통한 디자인 구현

디자인 이미지를 대화에 붙여넣으면 Claude가 이를 참고해 UI를 구현한다.

[디자인 이미지 붙여넣기]
이 디자인대로 React 컴포넌트 만들어줘. 완성되면 실행해서 스크린샷 찍어서 비교해줘

Claude가 컴포넌트를 구현하고, 브라우저에서 실행한 뒤, 스크린샷을 찍어 원본 디자인과 비교한다. 차이가 있으면 수정하고 다시 비교하는 과정을 반복한다.

CI/CD 통합

비대화형(non-interactive) 환경에서 Claude Code를 사용하면 CI 파이프라인에 통합할 수 있다.

claude -p "lint 에러 고쳐줘" --permission-mode auto

-p 플래그는 단일 작업을 처리하고 종료하는 print 모드다. --permission-mode auto는 사용자 확인 없이 자율적으로 작업을 처리하도록 설정한다. 이 조합을 사용하면 GitHub Actions나 Jenkins 같은 CI 환경에서 Claude를 실행할 수 있다.

# GitHub Actions 예시
- name: Fix lint errors
  run: claude -p "lint 에러 고쳐줘" --permission-mode auto
  env:
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}

효과적인 작업 지시 패턴

Claude Code에서 효율적인 결과를 얻으려면 지시 방식이 중요하다.

구체적으로 지시한다

모호한 요청은 모호한 결과를 낳는다. 파일명, 함수명, 예상 동작을 명시할수록 Claude가 의도에 맞는 결과를 내놓는다.

# 모호한 지시
로그인 기능 개선해줘

# 구체적인 지시
src/auth/login.ts의 authenticate 함수에서 비밀번호 해싱을 bcrypt 대신 argon2로 교체해줘.
인터페이스는 그대로 유지하고 내부 구현만 변경해.

반복 수정 시 /clear 후 재시작

같은 요청을 두세 번 반복 수정했는데도 원하는 결과가 나오지 않는다면 대화 히스토리가 방해가 되는 경우가 많다. /clear로 컨텍스트를 초기화하고 더 명확한 프롬프트로 새로 시작하는 편이 낫다.

이전 시도에서 "이렇게 하면 안 된다"는 사실을 확인했다면, 재시작할 때 그 내용을 함께 전달한다.

/clear
payment.service.ts의 refund 로직을 수정해줘.
주의: stripe SDK의 refund() 메서드를 직접 호출하지 말고
내부 RefundQueue를 통해 처리해야 해.

큰 작업은 분할한다

한 번의 요청에 너무 많은 작업을 담으면 Claude가 중요한 세부 사항을 놓치거나 부분적으로만 처리한다. 하나의 요청은 하나의 관심사에 집중한다.

# 좋지 않은 방법: 한 번에 너무 많은 요청
인증 모듈 전체를 JWT로 교체하고, 관련 테스트 모두 작성하고,
API 문서도 업데이트하고, CHANGELOG도 써줘

# 좋은 방법: 단계적 처리
1. "인증 모듈을 JWT 기반으로 교체해줘"  →  완료 후 검토
2. "방금 수정한 인증 모듈에 대한 테스트 작성해줘"  →  완료 후 검토
3. "변경 사항을 API 문서에 반영해줘"  →  완료

일일 워크플로우 체크리스트

실무에서 Claude Code를 사용하는 일반적인 하루의 흐름이다.

작업 시작 전

  • 작업 브랜치 생성 또는 전환
  • 필요시 워크트리로 격리 환경 구성
  • Claude Code 세션 시작

  • 구현 완료 후 테스트 실행 요청
  • 테스트 통과 확인 후 커밋

작업 완료 후

  • claude commit으로 변경 사항 정리 커밋
  • 필요시 PR 생성 및 리뷰 요청

핵심 정리

  • claude commit은 스테이징된 변경 사항을 분석해 커밋 메시지를 자동 생성한다. CLAUDE.md에 형식을 명시하면 팀 컨벤션을 일관되게 유지한다.
  • Plan Mode(Shift+Tab)로 대규모 작업 전에 변경 범위를 먼저 확인하고, Ctrl+G로 계획을 에디터에서 직접 편집할 수 있다.
  • git worktree와 멀티 세션을 조합하면 독립된 컨텍스트에서 여러 브랜치를 동시에 작업할 수 있다.
  • 응답이 짧아지거나 엉뚱한 파일을 참조하면 컨텍스트 한계 신호다. /clear로 전체 초기화하거나 /compact로 압축한다.
  • 서브에이전트는 탐색과 구현을 분리해 메인 컨텍스트를 보호한다. Ctrl+T로 진행 상황을, Ctrl+B로 백그라운드 전환을 제어한다.
  • "테스트 작성하고 통과하면 커밋해줘" 패턴으로 작성·검증·커밋을 하나의 흐름으로 처리한다.
  • 반복 수정이 통하지 않으면 /clear 후 더 구체적인 프롬프트로 재시작한다.

Ctrl+C vs Ctrl+D

두 단축키는 역할이 다르다. Ctrl+C는 현재 작업(생성 중인 응답, 실행 중인 명령)을 중단하고 프롬프트로 돌아온다. 세션은 그대로 유지된다. Ctrl+D는 세션 자체를 종료하는 EOF(End of File, 파일 끝) 신호다. 응답을 멈추고 싶다면 Ctrl+C, 세션을 끝내고 싶다면 Ctrl+D를 쓴다.

\ + Enter 백슬래시 이스케이프 — 어떤 터미널에서도 동작하는 가장 범용적인 방법

Shift+Enter iTerm2, WezTerm, Ghostty, Kitty에서 기본 지원. VS Code, Alacritty, Zed, Warp는 /terminal-setup 명령으로 바인딩을 설치해야 한다
Ctrl+J 범용 개행 문자 삽입 — 터미널 설정에 관계없이 대부분 동작

터미널 종류에 따라 지원 여부가 다르다. 현재 환경에서 어떤 방법이 작동하는지 짧게 테스트해 두면 편하다.

Bash 모드

프롬프트 앞에 !를 붙이면 해당 입력을 Claude에게 전달하지 않고 셸(shell)에서 직접 실행한다.

! npm test
! git status
! ls -la src/

Claude에게 "npm test 실행해줘"라고 부탁하는 것과 결과는 같지만, 중간 과정이 없다. 명령이 즉시 실행되고 출력이 실시간으로 터미널에 표시된다. 실행 결과는 자동으로 대화 컨텍스트에 추가되므로 Claude가 이어서 분석할 수 있다.

자동완성 지원

! 뒤에 명령을 입력할 때 터미널 자동완성이 동작한다. 경로나 명령어 이름을 Tab으로 완성할 수 있다.

키 조합 사이를 공백으로 구분해 작성한다. 두 번째 키를 일정 시간 내에 누르지 않으면 첫 번째 키 단독 동작으로 처리된다.

Chapter 08

하네스 엔지니어링

문서 메타

난이도: 중급~심화 | 선행 문서: Claude Code 시작하기

프롬프트 엔지니어링과 하네스 엔지니어링의 차이를 이해하고, Claude Code의 하네스를 체계적으로 설계하는 방법을 다룬다.

1. 프롬프트 엔지니어링의 한계

프롬프트 엔지니어링은 Claude에게 원하는 결과를 얻기 위해 입력 텍스트를 최적화하는 기법이다. 역할 부여, Chain of Thought, Few-shot, XML 태그 활용 — 이 기법들은 강력하고 여전히 유효하다. 하지만 실무에서 반복적으로 쓰다 보면 근본적인 한계에 부딪힌다.

반복의 문제

매 세션을 시작할 때마다 같은 지시를 반복해야 한다.

"한국어로 응답해줘. 커밋 메시지도 한국어로.
테스트는 npm test로 실행하고, 코드 스타일은 Prettier를 따라.
외부 라이브러리는 번들 크기 때문에 함부로 추가하지 마."

이 지시를 어제도 했고 오늘도 해야 하고 내일도 해야 한다. 프롬프트 엔지니어링은 본질적으로 일회성이다. 세션이 끝나면 맥락도 사라진다.

일관성의 문제

같은 팀의 두 개발자가 같은 프로젝트에서 Claude Code를 쓴다고 하자. 한 명은 "커밋 메시지를 한국어로 써줘"라고 프롬프트하고, 다른 한 명은 이 지시를 잊는다. 결과적으로 git 로그에 한국어와 영어 커밋 메시지가 뒤섞인다. 프롬프트 엔지니어링은 개인의 기억력에 의존하기 때문에 팀 수준의 일관성을 보장할 수 없다.

자동화의 부재

"파일을 수정할 때마다 자동으로 포맷팅해줘" — 이 요청을 매번 프롬프트로 전달하면 Claude가 잊을 수도 있고, 실행 순서가 꼬일 수도 있다. 프롬프트는 요청이지 명령이 아니다. Claude가 요청을 "해석"하는 과정에서 누락이 생길 수 있다. 자동화가 필요한 작업은 프롬프트가 아니라 시스템 수준에서 보장해야 한다.

새 직원 비유의 확장

프롬프트 엔지니어링을 설명할 때 흔히 "Claude는 유능한 신입 직원"이라는 비유를 쓴다. 맞는 말이다. 하지만 유능한 신입에게 매일 출근할 때마다 "우리 팀은 코드 리뷰를 이렇게 하고, 배포 절차는 이렇고, 커밋 메시지는 이 형식을 따르고..."라고 반복 설명하는 사람은 없다. 실제 직장에서는 온보딩 문서, 팀 위키, CI/CD 파이프라인, 린트 설정이 이 역할을 대신한다.

하네스 엔지니어링은 Claude Code 환경에서 이 "온보딩 인프라"를 구축하는 것이다.

2. 하네스 엔지니어링이란

하네스(harness)는 원래 "마구"라는 뜻이다. 말의 힘을 제어하고 방향을 잡아주는 도구다. 하네스 엔지니어링은 Claude의 능력을 프로젝트에 맞게 제어하고 방향을 잡아주는 영구적인 환경을 설계하는 방법론이다.

프롬프트 엔지니어링이 "매번 무엇을 말할 것인가"의 기술이라면, 하네스 엔지니어링은 "한 번 어떻게 세팅할 것인가"의 기술이다.

핵심 차이 비교

비교 항목 프롬프트 엔지니어링 하네스 엔지니어링
적용 시점 매 요청마다 프로젝트 설정 시 한 번
지속성 세션 종료 시 소멸 파일로 영구 저장
팀 공유 개인의 노하우에 의존 git으로 버전 관리·공유
일관성 사람이 기억해야 함 시스템이 자동 적용
자동화 불가능 (요청 기반) 이벤트 기반 자동 실행
버전 관리 불가능 git diff로 변경 이력 추적
범위 제어 프롬프트 전체에 적용 특정 파일·디렉토리에만 선택 적용
비용 매 요청마다 토큰 소비 한 번 설정하면 추가 비용 최소화

둘은 대체 관계가 아니다

하네스 엔지니어링이 프롬프트 엔지니어링을 대체하는 것은 아니다. 둘은 보완 관계다.

하네스는 반복되는 맥락과 규칙을 담당한다. "이 프로젝트는 TypeScript를 쓰고, 테스트는 Jest로 실행하며, 커밋 메시지는 한국어로 작성한다" — 이런 것은 한 번 설정하면 된다.

프롬프트는 일회성 작업 지시를 담당한다. "이 함수의 성능을 개선해줘", "이 버그를 분석해줘" — 이런 것은 매번 달라지므로 프롬프트로 전달한다.

좋은 하네스가 갖춰지면 프롬프트가 짧아진다. "한국어로, Prettier 형식으로, 테스트 통과 후 커밋해줘"라고 매번 덧붙일 필요 없이 "이 함수 성능 개선해줘"만 말하면 된다. 나머지는 하네스가 처리한다.

3. Claude Code 하네스의 6대 레이어

Claude Code의 하네스는 여섯 개의 레이어로 구성된다. 각 레이어는 서로 다른 역할을 담당하며, 조합해서 사용할 때 가장 강력하다.

┌─────────────────────────────────────────────┐
│              MCP 서버 (도구 확장)              │
├─────────────────────────────────────────────┤
│              Skills (워크플로우)               │
├─────────────────────────────────────────────┤
│              Hooks (자동화)                   │
├─────────────────────────────────────────────┤
│           settings.json (설정/권한)            │
├─────────────────────────────────────────────┤
│          .claude/rules/ (조건부 규칙)          │
├─────────────────────────────────────────────┤
│            CLAUDE.md (지침)                   │
└─────────────────────────────────────────────┘

아래에서 위로 갈수록 추상화 수준이 높아진다. CLAUDE.md는 "무엇을 해야 하는가"를 텍스트로 전달하고, MCP 서버는 "외부 세계와 어떻게 연결하는가"를 프로토콜로 정의한다.

3.1 CLAUDE.md — 지침 레이어

CLAUDE.md는 하네스의 토대다. Claude Code가 세션을 시작할 때 자동으로 읽어 프로젝트 맥락을 파악하는 지침 파일이다. API의 시스템 프롬프트와 같은 역할을 하지만, 파일로 존재하기 때문에 git으로 관리할 수 있다.

무엇을 담는가

프로젝트 정체성: 이 프로젝트가 무엇인지 한 줄로 정의한다. Claude가 작업의 맥락을 즉시 파악하는 출발점이 된다.

- 주 언어: TypeScript (프론트엔드 React, 백엔드 NestJS)
- 주 소통 언어: 한국어 (커밋 메시지, 코드 리뷰, 문서)

빌드·테스트 명령어: Claude가 추측하지 않고 올바른 명령을 실행하도록 정확한 명령어를 명시한다.

## Commands
- 테스트: `npm run test -- --watch=false`
- 린트: `npm run lint`
- 빌드: `npm run build`
- 단일 테스트: `npm run test -- --testPathPattern="파일명"`

코드 컨벤션: 자동 포매터로 강제되지 않는 팀 고유의 규칙을 적는다. 이 규칙들은 코드를 읽는 것만으로는 Claude가 추론하기 어려운 것들이다.

## Code Style
- 함수명은 동사로 시작한다 (get, create, validate, process)
- 에러 처리는 반드시 커스텀 AppError 클래스를 사용한다
- 외부 라이브러리 추가 시 번들 크기 영향을 먼저 확인한다
- DB 쿼리는 ORM 대신 쿼리 빌더(Knex)를 사용한다

금지사항: Claude가 하면 안 되는 일을 명시한다. 이유를 함께 적으면 Claude가 유사한 상황에서도 올바르게 판단한다.

## Don't
- .env, .env.production 파일을 수정하지 않는다 (보안 민감 파일)
- prisma migrate를 직접 실행하지 않는다 (DBA 승인 필요)
- console.log를 프로덕션 코드에 남기지 않는다 (로깅은 winston 사용)

계층 구조

CLAUDE.md는 세 계층으로 동작하며, 상위 계층이 우선한다.

계층 위치 관리 주체 용도
관리 정책 OS별 시스템 경로 조직 관리자 보안 정책, 사내 규정
프로젝트 ./CLAUDE.md 또는 ./.claude/CLAUDE.md 팀 (git 커밋) 프로젝트 컨벤션
사용자 ~/.claude/CLAUDE.md 개인 개인 작업 스타일

팀 전체에 적용할 규칙은 프로젝트 레벨에, 개인 취향(응답 언어, 출력 형식 등)은 사용자 레벨에 배치한다.

크기 관리

CLAUDE.md는 Claude의 컨텍스트 창을 직접 소비한다. 200줄 미만을 목표로 하되, 긴 참조 문서는 @문법으로 외부 파일을 참조한다.

# 프로젝트 지침

@README.md
@docs/architecture.md
@package.json

@파일경로를 쓰면 CLAUDE.md 자체는 간결하게 유지하면서 필요한 맥락을 Claude에게 제공할 수 있다.

3.2 .claude/rules/ — 조건부 규칙 레이어

CLAUDE.md가 프로젝트 전체에 적용되는 규칙이라면, .claude/rules/는 특정 파일이나 디렉토리에만 적용되는 조건부 규칙이다.

구조

.claude/
  rules/
    backend.md          # 백엔드 코드에만 적용
    frontend.md         # 프론트엔드 코드에만 적용
    testing.md          # 테스트 파일에만 적용
    api-contracts.md    # API 관련 파일에만 적용

paths 필드로 범위 지정

각 규칙 파일 상단에 YAML frontmatter를 작성해 적용 범위를 지정한다.

---
paths:
  - "src/api/**"
  - "src/routes/**"
---

# API 규칙

- 모든 엔드포인트는 입력값 유효성 검사를 포함해야 한다
- 응답 형식은 `{ data, error, meta }` 구조를 따른다
- HTTP 상태 코드는 REST 표준에 맞게 사용한다 (200, 201, 400, 401, 403, 404, 500)
- 페이지네이션은 cursor 기반을 사용한다 (offset 기반 금지)

Claude가 src/api/ 하위 파일을 작업할 때만 이 규칙이 로드된다. 프론트엔드 작업 중에는 컨텍스트를 차지하지 않는다.

왜 CLAUDE.md와 분리하는가

모든 규칙을 CLAUDE.md 하나에 넣으면 파일이 비대해진다. 백엔드 개발자가 프론트엔드 규칙을 매번 로드할 필요도 없다. rules/를 쓰면 두 가지 이점이 생긴다.

첫째, 컨텍스트 효율성이다. 필요한 규칙만 로드하므로 실제 작업에 쓸 수 있는 컨텍스트가 늘어난다.

둘째, 관리 편의성이다. API 규칙을 수정할 때 CLAUDE.md 전체를 건드리지 않고 api-contracts.md만 수정하면 된다.

3.3 settings.json — 설정 레이어

settings.json은 Claude Code의 동작 방식을 제어하는 JSON 설정 파일이다. CLAUDE.md가 "무엇을 하라"는 지침이라면, settings.json은 "어떤 도구를 쓸 수 있고 어떤 권한이 있는가"를 정의한다.

세 계층

~/.claude/settings.json          # 글로벌: 모든 프로젝트 공통
.claude/settings.json            # 프로젝트: 팀과 공유 (git 커밋)
.claude/settings.local.json      # 로컬: 개인 전용 (git 제외)

핵심 설정 항목

권한 설정: Claude가 확인 없이 실행할 수 있는 도구를 정의한다.

{
  "permissions": {
    "allow": [
      "Bash(git:*)",
      "Bash(npm test:*)",
      "Bash(npx jest:*)",
      "Read",
      "Glob",
      "Grep"
    ],
    "deny": [
      "Bash(rm -rf:*)",
      "Bash(git push --force:*)"
    ]
  }
}

allow에 등록된 도구는 매번 확인 없이 실행된다. deny에 등록된 명령은 항상 차단된다. 이 설정이 없으면 Claude가 git status를 실행할 때마다 "허용할까요?"라는 프롬프트가 뜬다.

환경 변수: Claude Code 실행 환경에 필요한 변수를 정의한다.

{
  "env": {
    "NODE_ENV": "development",
    "LOG_LEVEL": "debug"
  }
}

프로젝트 설정 vs 로컬 설정

팀 전체에 강제할 설정(허용 도구, 금지 명령)은 .claude/settings.json에 넣고 git에 커밋한다. API 키처럼 개인마다 다른 값은 .claude/settings.local.json에 넣어 git에서 제외한다.

3.4 Hooks — 자동화 레이어

Hook은 Claude Code의 특정 이벤트에 반응해 자동으로 실행되는 명령이다. 앞의 세 레이어(CLAUDE.md, rules, settings)가 Claude에게 "이렇게 해라"고 텍스트로 전달하는 지침이라면, Hook은 "이 이벤트가 발생하면 이 명령을 실행하라"는 기계적 자동화다.

지침과 자동화의 차이는 중요하다. CLAUDE.md에 "파일 수정 후 prettier를 실행하라"고 쓰면 Claude가 이 지시를 해석하고 판단해서 실행한다. 가끔 빼먹을 수 있다. Hook으로 설정하면 파일이 수정될 때마다 시스템이 무조건 실행한다. 빼먹을 여지가 없다.

주요 이벤트

아래는 자주 사용되는 주요 이벤트다. 전체 목록(25개 이상)은 공식 문서를 참고한다.

이벤트 발생 시점 차단 가능
SessionStart 세션 시작/재개 아니오
PreToolUse 도구 실행 직전 예
PostToolUse 도구 실행 성공 후 아니오
PermissionRequest 권한 확인 프롬프트 표시 시 예
UserPromptSubmit 사용자 메시지 제출 시 예
Notification 알림 발생 시 아니오
Stop 응답 완료 시 아니오
SubagentStart 서브에이전트 시작 시 아니오
SubagentStop 서브에이전트 종료 시 아니오
SessionEnd 세션 종료 시 아니오

PreToolUse, PermissionRequest, UserPromptSubmit 등 차단 가능한 이벤트에서 Hook이 종료 코드 2를 반환하면 해당 작업이 실행되지 않는다.

4가지 Hook 타입

command: 셸 명령어를 직접 실행한다. 가장 일반적인 타입이다.

{
  "type": "command",
  "command": "npx prettier --write \"$TOOL_INPUT_FILE_PATH\" 2>/dev/null || true"
}

prompt: Claude(Haiku 모델)에게 판단을 맡긴다. 규칙 기반으로 처리하기 어려운 맥락적 판단에 적합하다.

{
  "type": "prompt",
  "prompt": "이 파일 편집이 보안에 영향을 줄 수 있는지 확인하라."
}

agent: 서브에이전트를 별도로 실행해 복잡한 검증 작업을 맡긴다.

{
  "type": "agent",
  "agent": "security-reviewer",
  "prompt": "변경된 파일에서 SQL 인젝션 취약점을 검토하라."
}

http: HTTP 엔드포인트를 호출한다. 외부 서비스 연동이나 웹훅 전송에 사용한다.

{
  "type": "http",
  "url": "https://hooks.slack.com/services/...",
  "method": "POST"
}

실전 패턴

자동 포맷팅 — 파일 편집 후 prettier가 자동으로 실행된다.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npx prettier --write \"$TOOL_INPUT_FILE_PATH\" 2>/dev/null || true"
          }
        ]
      }
    ]
  }
}

보호 파일 차단 — .env 파일 수정을 사전에 막는다.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "python3 -c \"\nimport json, sys\ndata = json.load(sys.stdin)\npath = data.get('tool_input', {}).get('file_path', '')\nprotected = ['.env', '.env.production', 'secrets.yaml']\nif any(p in path for p in protected):\n    print(f'차단: {path}는 보호된 파일입니다.')\n    sys.exit(2)\n\""
          }
        ]
      }
    ]
  }
}

안전한 명령 자동 승인 — git status, npm test 같은 읽기 전용 명령은 확인 없이 실행한다.

{
  "hooks": {
    "PermissionRequest": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 -c \"\nimport json, sys\ndata = json.load(sys.stdin)\ncmd = data.get('tool_input', {}).get('command', '')\nsafe = ['git status', 'git log', 'git diff', 'npm test', 'npx jest']\nif any(cmd.startswith(p) for p in safe):\n    sys.exit(0)\nelse:\n    sys.exit(1)\n\""
          }
        ]
      }
    ]
  }
}

3.5 Skills — 워크플로우 레이어

스킬은 반복적인 작업 절차를 캡슐화한 재사용 단위다. CLAUDE.md가 "어떤 규칙을 따르라"고 지시한다면, 스킬은 "이 작업을 이 절차로 수행하라"는 구체적인 워크플로우를 정의한다.

스킬이 해결하는 문제

"SRS를 IEEE 830 기준으로 작성해줘. FR에는 선행 조건과 예외 흐름을 포함하고, NFR에는 성능 수치를 명시하고, 인터뷰는 6단계로 진행하고..." — 이 프롬프트를 매번 쓸 수는 없다. 스킬로 만들면 /spec-writer라고 입력하는 것만으로 동일한 품질의 작업이 시작된다.

구조

skill-name/
├── SKILL.md          # 메인 지시문 (필수)
└── references/       # 템플릿, 카탈로그 등 보조 파일

SKILL.md는 frontmatter와 본문으로 구성된다.

---
name: spec-writer
version: 1.3.0
description: 시스템 요구사항 명세서(SRS)를 대화형 인터뷰를 통해 작성하는 스킬.
  "요구사항 명세서 작성해줘", "SRS 만들어줘" 같은 요청에 사용.
  단, 단순 기획서 작성이나 API 문서 자동생성 요청에는 사용하지 않는다.
---

## 핵심 원칙
...

## 워크플로우
요청 입력 → 인터뷰 6단계 → SRS 생성 → 리뷰
...

호출 방식

슬래시 명령으로 직접 호출: /spec-writer라고 입력하면 즉시 실행된다.

자동 감지: "요구사항 명세서 작성해줘"라고 자연어로 요청하면 Claude가 description을 읽고 적합한 스킬을 자동으로 선택한다.

자동 감지의 정확도는 description의 품질이 결정한다. 긍정 예시("SRS 만들어줘")와 부정 예시("Swagger 문서 생성은 사용하지 않는다")를 모두 포함해야 오작동을 줄일 수 있다.

설치 위치

위치 범위
~/.claude/skills/ 모든 프로젝트에서 사용하는 글로벌 스킬
.claude/skills/ 현재 프로젝트에서만 사용하는 프로젝트 스킬
skills/ (프로젝트 루트) 스킬을 관리하는 레포지토리에서 사용

프로젝트 스킬이 글로벌 스킬보다 우선한다. 같은 이름의 스킬이 두 곳에 있으면 프로젝트 스킬이 사용된다.

3.6 MCP 서버 — 도구 확장 레이어

MCP(Model Context Protocol)는 Claude가 외부 서비스와 상호작용하는 방식을 표준화한 프로토콜이다. 앞의 다섯 레이어가 Claude의 행동과 규칙을 제어한다면, MCP는 Claude가 접근할 수 있는 도구의 범위 자체를 확장한다.

Claude Code의 기본 도구

Claude Code는 기본적으로 파일 읽기/쓰기, 셸 명령 실행, git 작업을 수행할 수 있다. 이것이 Claude Code의 기본 도구 세트다. MCP 서버를 연동하면 이 세트에 새로운 도구가 추가된다.

주요 MCP 서버

GitHub MCP: 이슈 생성, PR 리뷰, 코드 조회를 Claude Code 세션 안에서 처리한다.

claude mcp add github -- npx @anthropic-ai/github-mcp

Playwright MCP: 웹 브라우저를 직접 제어해 페이지 탐색, 스크린샷, 폼 입력을 자동화한다.

claude mcp add playwright -- npx @playwright/mcp@latest

Notion MCP: 노션 페이지를 읽고 편집한다.

claude mcp add notion -- npx @anthropic-ai/notion-mcp

Context7 MCP: 외부 라이브러리의 공식 문서를 실시간으로 가져온다. Claude의 학습 데이터 기준일 이후 변경된 API를 정확히 참조할 때 유용하다.

claude mcp add context7 -- npx @context7/mcp

설정 파일

.mcp.json에 서버를 등록한다. 환경 변수로 민감한 값을 관리한다.

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["@anthropic-ai/github-mcp"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}

글로벌 설정(~/.claude.json)은 모든 프로젝트에, 프로젝트 설정(.mcp.json)은 해당 프로젝트에만 적용된다.

4. 하네스 설계 원칙

여섯 개 레이어를 개별적으로 이해하는 것과 이들을 조합해 효과적인 하네스를 설계하는 것은 다른 문제다. 아래 네 가지 원칙이 설계의 기본이다.

원칙 1: 레이어 간 역할 분리

각 레이어가 담당하는 질문이 다르다. 이 구분을 명확히 하면 같은 규칙이 여러 곳에 분산되는 것을 방지한다.

질문 담당 레이어
무엇을 해야 하는가? CLAUDE.md
이 파일을 다룰 때 특별히 지켜야 할 것은? .claude/rules/
어떤 도구를 쓸 수 있는가? settings.json
이벤트 발생 시 무엇을 자동으로 실행하는가? Hooks
이 작업을 어떤 절차로 수행하는가? Skills
어떤 외부 서비스와 연결하는가? MCP

예를 들어 "API 응답 형식은 { data, error, meta } 구조를 따른다"는 규칙은 .claude/rules/api-contracts.md에 둔다. "파일 수정 후 prettier를 실행한다"는 Hooks에 둔다. "SRS를 6단계 인터뷰로 작성한다"는 Skills에 둔다. 세 가지를 CLAUDE.md에 모두 넣으면 파일이 비대해지고 역할이 뒤섞인다.

원칙 2: 변경 빈도에 따른 배치

하네스의 각 레이어는 변경 빈도가 다르다. 자주 바뀌는 것과 거의 바뀌지 않는 것을 분리하면 관리가 쉬워진다.

변경 빈도 레이어 예시
거의 안 바뀜 CLAUDE.md, settings.json 프로젝트 정체성, 권한 정책
가끔 바뀜 .claude/rules/, Hooks 코딩 규칙 추가, 자동화 패턴 변경
자주 바뀜/발전 Skills, MCP 새 워크플로우 추가, 외부 도구 연동

CLAUDE.md를 매주 고쳐야 한다면 해당 내용은 rules/로 분리하는 것이 맞다. 반대로 settings.json을 자주 바꿔야 한다면 설계에 문제가 있을 가능성이 높다.

원칙 3: 팀 공유 vs 개인 설정 분리

하네스의 모든 요소를 팀에 공유할 필요는 없다.

git에 커밋해 팀과 공유하는 것:

파일 이유
CLAUDE.md 팀 컨벤션은 전원이 따라야 한다
.claude/settings.json 허용/금지 도구는 팀 정책이다
.claude/rules/ 코딩 규칙도 팀 전체에 적용된다
.mcp.json 프로젝트에 필요한 외부 도구는 공유한다

개인 환경에 두는 것:

파일 이유
~/.claude/CLAUDE.md 개인 작업 스타일
.claude/settings.local.json API 키, 개인 토큰
~/.claude/settings.json 개인 선호 모델, 권한 모드

원칙 4: 컨텍스트 예산 관리

하네스도 토큰을 소비한다. CLAUDE.md, rules, 스킬 본문은 모두 Claude의 컨텍스트 창에 로드된다. 하네스가 비대해지면 실제 작업에 쓸 수 있는 공간이 줄어든다.

  • CLAUDE.md는 200줄 미만을 목표로 한다
  • 긴 참조 문서는 @문법으로 분리한다
  • rules/의 paths 필드로 필요한 규칙만 로드한다
  • 스킬 본문은 간결하게, 상세 지식은 references/로 분리한다

컨텍스트 효율성은 단순히 토큰을 아끼는 문제가 아니다. 불필요한 정보가 많으면 Claude가 핵심 지시를 놓칠 확률도 높아진다.

5. 프롬프트에서 하네스로: 전환 패턴

프롬프트 엔지니어링에서 하네스 엔지니어링으로 전환하는 것은 한 번에 일어나지 않는다. "이 프롬프트를 또 쓰고 있네"라는 순간이 하네스로 옮길 신호다.

패턴 1: 반복 지시 → CLAUDE.md

Before — 매 세션 시작마다:

7. 다른 플랫폼의 하네스 메커니즘

하네스 엔지니어링은 Claude Code에만 존재하는 개념이 아니다. 다른 LLM 도구들도 유사한 메커니즘을 제공한다. 비교하면 Claude Code의 하네스가 어떤 위치에 있는지 더 잘 이해할 수 있다.

OpenAI Custom GPTs

OpenAI의 Custom GPTs는 세 가지 구성 요소로 하네스를 제공한다.

  • Instructions: 시스템 프롬프트에 해당한다. Claude Code의 CLAUDE.md와 유사하지만 파일이 아니라 웹 UI에서 설정하므로 git 관리가 불가능하다.
  • Actions: 외부 API를 OpenAPI 스펙으로 연동한다. Claude Code의 MCP 서버와 유사한 역할이지만, 프로토콜 표준화 수준에서 차이가 있다.
  • Knowledge: 참조 문서를 업로드한다. Claude Code의 @문법 파일 참조와 비슷하다.

Custom GPTs는 설정이 간편하지만 이벤트 기반 자동화(Hooks)나 조건부 규칙(rules/)에 해당하는 기능이 없다.

Cursor (.cursorrules)

Cursor IDE는 .cursorrules 파일로 프로젝트 수준 지침을 제공한다. Claude Code의 CLAUDE.md와 유사한 역할이다. 단, Cursor는 단일 파일 방식이므로 Claude Code의 .claude/rules/처럼 파일별 조건부 규칙을 분리하는 기능은 지원하지 않는다.

Claude Code의 하네스가 가장 풍부한 레이어 구조를 제공한다. 특히 Hooks에 의한 이벤트 기반 자동화와 Skills에 의한 워크플로우 캡슐화는 다른 도구에서 찾기 어려운 기능이다.

8. 핵심 정리

한 줄 요약

프롬프트 엔지니어링이 "매번 무엇을 말할 것인가"의 기술이라면, 하네스 엔지니어링은 "한 번 어떻게 세팅할 것인가"의 기술이다.

하네스 도입 체크리스트

기본 (당장 시작)

  • CLAUDE.md에 프로젝트 정체성, 주 언어, 빌드/테스트 명령을 적었는가?
  • 반복적으로 프롬프트하던 지시를 CLAUDE.md로 옮겼는가?
  • settings.json에 자주 쓰는 도구를 allow 목록에 추가했는가?

중급 (익숙해지면)

  • .claude/rules/에 영역별 규칙을 분리했는가?
  • PostToolUse Hook으로 자동 포맷팅을 설정했는가?
  • PreToolUse Hook으로 보호 파일 수정을 차단했는가?
  • GitHub MCP 서버를 연동했는가?

심화 (팀 운영)

  • 반복 워크플로우를 Skills로 캡슐화했는가?
  • 팀 공유 설정과 개인 설정을 분리했는가?
  • 하네스 전체를 git에 커밋해 팀과 공유하고 있는가?
  • 새 팀원이 git clone만으로 동일한 환경을 갖추는가?
