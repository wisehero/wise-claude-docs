# 보리스 체르니의 Claude Code 설계 사상

> **난이도**: 전체 | **선행 문서**: `claude-code/01-시작하기.md` | **최초 작성**: 2026-04-25 | **마지막 수정**: 2026-04-25
>
> Anthropic의 Head of Claude Code인 Boris Cherny가 공개 인터뷰·트윗·팟캐스트에서 밝힌 Claude Code 설계 철학과 사용 방식을 정리한다.

---

## 1. 인물 배경

Boris Cherny는 Claude Code의 creator이자 현재 Anthropic의 Head of Claude Code다. 2024년 9월 Anthropic에 합류한 founding engineer로, Claude 3.6 모델로 Claude Code 초기 프로토타입을 만들었다. Anthropic 합류 전에는 Meta의 Principal Engineer였고, O'Reilly의 *Programming TypeScript* 저자이기도 하다.

이 문서는 이 가이드 레포의 다른 문서들과 달리 한 사람의 생각을 모은 것이다. 공식 문서가 "무엇을 할 수 있는가"를 다룬다면, 이 문서는 "왜 그렇게 만들었는가"를 다룬다.

---

## 2. 코딩이 해결된 후 무엇이 남는가

2026년 2월 Lenny's Podcast에서 Boris는 다음과 같이 선언했다.

> "I think at this point it's safe to say that **coding is largely solved**."

지난 30일간 자기 코드의 100%를 Claude Code로 썼다고 밝혔다. 그렇다면 엔지니어의 일은 사라지는가? 그의 답은 아니다 — **컨텍스트 스위칭이 새로운 핵심 역량**이다.

> "It's not so much about deep work, it's about how good I am at context switching and jumping across multiple different contexts very quickly."

Anthropic 내부 채용 기준도 이 방향으로 움직였다. PM, 데이터 사이언티스트, UX 리서처 모두 코딩이 가능한 generalist를 우선한다. 코드 작성 비용이 떨어지면서 "한 사람이 여러 역할을 동시에 들고 가는" 모델이 효율적이 되었기 때문이다.

출처: [Lenny's Newsletter — Head of Claude Code: What happens after coding is solved](https://www.lennysnewsletter.com/p/head-of-claude-code-what-happens), [Pragmatic Engineer — Building Claude Code with Boris Cherny](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny)

## 3. 6개월 후의 모델을 위해 만든다

Y Combinator Lightcone 팟캐스트에서 한 발언이다.

> "At Anthropic, we don't build for the model of today, we build for the model of six months from now."

이 원칙은 Claude Code의 디자인 결정 곳곳에 반영되어 있다. 모델이 더 똑똑해질 것을 전제로 하니, 하네스(harness) 자체는 가능한 한 minimal하게 두고, 모델이 직접 처리할 수 있는 일은 도구로 감싸지 않는다. 도구는 "지금 모델이 못하는 것"을 보완할 뿐이고, 6개월 후 모델이 해결하면 도구는 제거된다.

이 철학은 실제 코드 비율로도 드러난다. Claude Code 코드의 80~90%가 Claude 자체로 작성됐다고 Latent Space 팟캐스트에서 밝혔다.

출처: [Y Combinator X post](https://x.com/ycombinator/status/2026787362693591205), [Latent Space — Claude Code](https://www.latent.space/p/claude-code)

## 4. 검증 가능성이 품질을 2-3배 높인다

2026년 1월 Boris의 X 스레드에서 가장 많이 인용된 문장이다.

> "The most important thing to get great results out of Claude Code — give Claude a way to verify its work... it will 2-3x the quality of the final result."

구체적 수단으로 그가 든 것은 다음 네 가지다.

- 테스트 스위트
- 브라우저 프리뷰 (UI 작업의 경우)
- Lint
- 타입 체커

핵심은 "Claude가 자기 결과를 스스로 확인할 수 있는 수단을 명시적으로 제공하라"이다. 이 수단이 있으면 Claude가 반복적으로 자가 수정을 한다. 없으면 첫 결과물에서 멈춘다.

이 인사이트는 이 가이드의 `claude-code/06-실전-워크플로우.md`에서 다루는 "TDD 루프", "프리뷰 기반 UI 반복" 패턴의 근거이기도 하다.

출처: [Boris Cherny X Thread](https://twitter-thread.com/t/2007179832300581177)

## 5. 정답은 없다 — 자기 워크플로우를 만들어라

Boris는 Claude Code 설계 의도를 다음과 같이 요약한다.

> "There is no one correct way to use Claude Code: we intentionally build it in a way that you can use it, customize it, and hack it however you like."

Claude Code 팀 내부에서도 사람마다 사용 방식이 다르다. Boris 본인은 Opus 4.5(현재는 4.7) + thinking만 쓴다고 밝혔다. 모델 응답이 느려도, 결과물의 정확도가 높아 결국 그의 시간을 덜 잡아먹기 때문이다 — "조종 비용(steering cost)"이 낮을수록 토탈 효율이 높다는 관점.

이 관점은 [howborisusesclaudecode.com](https://howborisusesclaudecode.com/)에서 본인 워크플로우 전체로 공개되어 있다.

출처: [Boris Cherny X Thread](https://twitter-thread.com/t/2007179832300581177), [How Boris Uses Claude Code](https://howborisusesclaudecode.com/)

## 6. 병렬화가 최적화를 이긴다

Pragmatic Engineer 인터뷰(Gergely Orosz, 2026년)에서 Boris의 일과가 공개됐다.

- 터미널 5개 + 웹 5~10개 = 동시 10~15개의 Claude 세션
- Plan mode로 계획 먼저 세우고 → one-shot 구현
- 하루 PR 발송 수: **20~30개**

핵심 메시지는 "Parallelization beats optimization" — 한 작업을 더 잘 시키려고 튜닝하기보다, 여러 작업을 동시에 돌리는 것이 결과적으로 빠르다는 것이다. 이 패턴은 모델이 답변하는 동안 인간이 노는 시간을 없애는 방향으로 작동한다.

이는 다른 멀티에이전트 패턴(예: oh-my-claudecode)이 등장한 배경과도 맞닿아 있다.

출처: [Pragmatic Engineer Interview](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny)

## 7. 마이그레이션은 끝까지 — 안전한 default의 원칙

Pragmatic Engineer 인터뷰에서 Boris가 든 사례 중 하나.

> "always make sure that when you start a migration, you finish the migration"

부분 완료된 마이그레이션을 코드베이스에 남기지 않도록 시스템이 강제해야 한다는 원칙이다. 에이전트가 중간에 멈춘 채 끝났다고 보고하는 가장 흔한 실패 모드를 차단하는 디폴트.

이 사고방식은 Claude Code의 권한 모드(`acceptEdits`, `plan`), `/clear` 동작, hook 시스템 같은 곳에 반영되어 있다 — "에이전트가 중간에 그만두면 안 되는 작업"을 시스템이 인식하고 끝까지 끌고 가도록 설계된 것.

출처: [Pragmatic Engineer Interview](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny)

## 8. 핵심 정리

Boris의 발언을 한 줄씩 요약하면 다음과 같다.

| 주제 | 한 줄 요약 |
|---|---|
| 코딩의 미래 | 코딩은 해결됐고, 컨텍스트 스위칭이 새 핵심 역량 |
| 설계 시간 지평 | 오늘 모델이 아닌 6개월 후 모델을 위해 만든다 |
| 품질의 핵심 | Claude에게 검증 수단을 줘라 (2-3배 효과) |
| 사용 방식 | 정답 없음, 각자 자기 워크플로우를 만들어라 |
| 효율의 본질 | 한 작업 최적화보다 병렬화 |
| 안전한 default | 시작한 작업은 끝까지 — 부분 완료 금지 |

이 사상들이 Claude Code의 동작 방식, 디폴트 설정, 권장 워크플로우 곳곳에 녹아 있다. 도구를 쓰면서 "왜 이렇게 동작하지?"가 떠오를 때 이 사고 모델로 돌아가면 답이 보일 때가 많다.
