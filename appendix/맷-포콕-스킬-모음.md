## 1. 왜 이 모음집이 화제가 됐나

Matt Pocock의 표현을 그대로 옮기면 다음과 같다.

> "My agent skills that I use every day to do real engineering — not vibe coding."

GSD, BMAD, Spec-Kit처럼 "프로세스 자체를 통째로 가져가는" 프레임워크와 다르게, 이 스킬들은 **작고, 고치기 쉽고, 조립 가능하다(small, easy to adapt, composable)**. 한 스킬이 한 가지 실패 모드만 잡는다. 모델 종류도 가리지 않는다.

이 가이드의 [커스텀 스킬 문서](../claude-code/03-커스텀-스킬.md)에서 다룬 SKILL.md 구조의 모범 사례를 한 사람의 워크플로우 안에서 일관되게 보고 싶다면 이 저장소가 가장 좋은 표본이다.

## 2. 그가 진단한 4대 실패 모드

README는 스킬 카탈로그가 아니라 "에이전트 코딩에서 반복되는 4가지 실패 모드"의 진단서로 시작한다. 스킬 하나하나는 이 진단의 처방으로 매핑된다.

### 실패 #1 — "에이전트가 내가 원한 걸 안 만들었다"

> "No-one knows exactly what they want."
> — David Thomas & Andrew Hunt, *The Pragmatic Programmer*

원인은 정렬(alignment) 부족이다. 처방은 **그릴링 세션** — 에이전트가 사용자에게 디테일한 질문을 끝까지 던지게 한다.

대응 스킬: `/grill-me`, `/grill-with-docs`

### 실패 #2 — "에이전트가 너무 장황하다"

원인은 공유 언어 부재다. 도메인 전문가와 개발자가 서로 다른 단어를 쓰는 고전적 문제가 에이전트와의 대화에도 그대로 재현된다. 처방은 `CONTEXT.md`로 **Ubiquitous Language**를 코드베이스 루트에 박아두는 것이다.

비교 예시(README 인용):

- BEFORE: "There's a problem when a lesson inside a section of a course is made 'real' (i.e. given a spot in the file system)"
- AFTER: "There's a problem with the materialization cascade"

대응 스킬: `/grill-with-docs` (CONTEXT.md와 ADR을 인터뷰 중에 같이 갱신한다)

### 실패 #3 — "코드가 안 돌아간다"

원인은 피드백 루프 부재다. Boris Cherny의 "검증 가능성이 품질을 2-3배 높인다"와 정확히 같은 진단이다([보리스 체르니 인사이트](보리스-체르니-인사이트.md) 참고).

대응 스킬: `/tdd` (red-green-refactor), `/diagnose` (재현 → 최소화 → 가설 → 계측 → 수정 → 회귀 테스트)

### 실패 #4 — "Ball of Mud을 만들었다"

> "Invest in the design of the system *every day*."
> — Kent Beck, *Extreme Programming Explained*

> "The best modules are deep."
> — John Ousterhout, *A Philosophy of Software Design*

에이전트가 코딩 속도를 높이면 소프트웨어 엔트로피도 같이 가속된다. 처방은 **모듈 깊이(depth)에 대한 집착**을 워크플로우 곳곳에 심는 것이다.

대응 스킬: `/to-prd` (모듈 단위 계획), `/zoom-out` (전체 맥락 이해), `/improve-codebase-architecture` (며칠에 한 번 돌리는 정기 점검)

## 3. 스킬 카탈로그

### 엔지니어링 (Engineering) — 매일 쓰는 코드 작업용

| 스킬 | 한 줄 요약 |
|------|------------|
| `diagnose` | 어려운 버그/성능 회귀 진단 루프. **Phase 1이 핵심 — 먼저 빠르고 결정론적인 pass/fail 피드백 루프부터 만들고 나머지는 그걸 소비할 뿐**이라고 못박는다 |
| `grill-with-docs` | 그릴링 세션 + 도메인 모델 검증. 결정이 굳을 때마다 `CONTEXT.md`와 `docs/adr/`를 인라인으로 갱신 |
| `triage` | 5개 상태(`needs-triage`/`needs-info`/`ready-for-agent`/`ready-for-human`/`wontfix`)의 state machine으로 이슈 처리. 모든 코멘트 머리에 `> *This was generated by AI during triage.*` 강제 |
| `improve-codebase-architecture` | "deepening opportunities" 발굴. **삭제 테스트(Deletion test)** 와 "어댑터 1개 = 가설적 seam, 2개 = 실제 seam" 같은 휴리스틱이 인상적 |
| `setup-matt-pocock-skills` | 다른 엔지니어링 스킬들이 공유하는 per-repo 설정(이슈 트래커, 트리아지 라벨, 도메인 문서 위치)을 한 번에 깔아주는 부트스트랩 스킬 |
| `tdd` | red-green-refactor를 **수직 슬라이스(tracer bullet)** 단위로. "horizontal slicing"(테스트 먼저 다 쓰고 구현 다 쓰기)을 명시적 안티패턴으로 못박는다 |
| `to-issues` | 계획·스펙·PRD를 독립적으로 잡을 수 있는(independently-grabbable) 이슈로 쪼갠다. 슬라이스는 HITL/AFK로 분류 |
| `to-prd` | 인터뷰 없이 현재 대화 컨텍스트를 PRD로 합성. 작성 단계에서 모듈 추출 기회를 적극 탐색 |
| `zoom-out` | 코드 한 부분만 보다 시야가 좁아졌을 때 한 단계 위 추상화로 올라가 모듈 지도를 받는다 |
| `prototype` | 버릴 프로토타입. 두 갈래로 분기 — *상태/로직 검증*은 터미널 인터랙티브, *UI 검증*은 한 라우트에서 토글되는 변형들. 6가지 공통 규칙(throwaway, one-command, no persistence, no polish, surface-the-state, delete-or-absorb)이 명료 |

출처: [skills/engineering 디렉토리](https://github.com/mattpocock/skills/tree/main/skills/engineering)

## 4. 가져갈 만한 설계 원칙

스킬을 그대로 쓸지 여부와 별개로, 그가 SKILL.md를 작성하는 방식에서 뽑을 수 있는 패턴이 몇 가지 있다.

### 4.1 description은 트리거 키워드를 나열한다

`diagnose`의 description을 보자.

> "Use when user says 'diagnose this' / 'debug this', reports a bug, says something is broken/throwing/failing, or describes a performance regression."

이 가이드의 [커스텀 스킬 문서](../claude-code/03-커스텀-스킬.md)에서도 강조하는 패턴이지만, Pocock은 이걸 **거의 모든 스킬에 일관되게** 적용한다. 동의어와 간접 표현(broken/throwing/failing 같은)까지 다 적어두면 스킬이 의도된 시점에 정확히 트리거된다.

### 4.2 "이게 핵심이다"를 본문에 명시한다

`diagnose`의 Phase 1 설명에 이런 문장이 있다.

> "**This is the skill.** Everything else is mechanical. ... Be aggressive. Be creative. Refuse to give up."

스킬 본문에 "이 단계에 비대칭적 노력을 쏟아라"고 명시적으로 쓰는 방식은 모델이 단계를 균등하게 분배해버리는 실패 모드를 막는다.

### 4.3 안티패턴을 따로 빼서 못박는다

`tdd`는 "horizontal slicing"을 별도 섹션으로 명명하고 그게 왜 crap tests를 만드는지 4가지 이유로 분해한다.

```
WRONG (horizontal):
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5
```

이 시각적 대비가 모델한테 강하게 박힌다.

### 4.4 용어집을 스킬 안에 박는다

`improve-codebase-architecture`는 *Module / Interface / Implementation / Depth / Seam / Adapter / Leverage / Locality* 8개 용어의 정의를 스킬 본문에 직접 박아두고, "이 단어를 정확히 그대로 써라(Use these terms exactly). 'component', 'service', 'API', 'boundary'로 표류하지 마라"고 못박는다.

이는 도메인 언어를 `CONTEXT.md`에 두는 것과 같은 사상이다 — 어휘가 일관되면 토큰을 적게 쓰고, 코드 네이밍도 일관되고, 에이전트 항법성이 좋아진다.

### 4.5 자동 해제 조건을 명시한다

`caveman`은 보안 경고, 비가역 작업 확인, 멀티스텝 시퀀스에서 단편 순서가 오독될 위험이 있는 경우 **모드를 일시 해제하고 끝나면 자동 복귀**한다고 본문에 명시한다. "토큰 절감"이라는 단일 목적이 사용자 안전을 침해하지 않도록 가드를 박은 것이다.

## 5. 이 가이드 레포에 적용한다면

이 저장소(`wise-claude-docs`)에는 이미 한국어 도메인 특화 스킬 8종이 있다(`code-analyzer`, `refactor-advisor`, `junit-test-writer` 등). Pocock의 모음집과 비교하면 다음과 같은 차이가 보인다.

| 측면 | Pocock의 스킬 | 이 가이드의 기존 스킬 |
|------|--------------|----------------------|
| 언어 | 영어 | 한국어 |
| 도메인 | 언어 중립 (TS 위주이긴 함) | Java/Spring 특화가 다수 |
| 단위 | 워크플로우 단계 (계획/이슈/진단) | 작업 종류 (테스트 작성/리팩토링/성능 분석) |
| 정렬 도구 | `grill-me`, `grill-with-docs`로 별도 분리 | 각 스킬 안에 인터뷰 단계 내장 |

**바로 가져올 만한 것**:

- `caveman` 패턴 — 한국어 버전으로 만들면 토큰 절약 효과가 영어보다 더 클 가능성이 있다(한국어가 토큰당 정보 밀도가 낮아 절감 여지가 더 큼)
- `grill-me`의 "한 번에 한 질문, 추천 답안 동반" 인터뷰 패턴 — `spec-writer`에 이미 있지만 다른 스킬에도 일반화 가능
- `improve-codebase-architecture`의 용어집 박기 — Java/Spring 컨벤션 용어로 번역하면 `refactor-advisor`의 진단 일관성이 올라간다

**그대로 가져오면 안 되는 것**:

- `setup-matt-pocock-skills` 같은 부트스트랩 스킬은 Pocock의 다른 스킬들이 공유하는 가정(`CONTEXT.md` 위치, ADR 디렉토리 구조)에 의존한다. 가져오려면 우리 도메인에 맞춰 재작성이 필요하다
- `migrate-to-shoehorn`, `scaffold-exercises`는 Total TypeScript 강의 인프라 전용이다
