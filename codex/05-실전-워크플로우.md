## 들어가며

이 문서는 Codex CLI를 이용해 실제 프로젝트에서 반복적으로 수행하는 작업들을 어떻게 처리하는지 구체적인 예시와 함께 설명한다. 기능 구현, 리팩토링, 버그 수정, 코드 리뷰, git 통합 패턴을 다룬다.

## 1. Git 연동 패턴

### 기능 브랜치에서 작업하기

Codex를 사용할 때는 항상 피처 브랜치에서 시작한다. 에이전트가 자동 승인 정책이나 `--full-auto` 프리셋으로 변경을 가할 수 있기 때문에, main 브랜치를 직접 보호한다.

```bash
git checkout -b feature/OC-123-add-order-status-api
codex
```

세션 내에서 작업을 완료한 뒤 변경 사항을 확인한다.

```bash
git diff
git status
```

결과가 만족스러우면 커밋한다.

```bash
git add src/
git commit -m "feat(order): 주문 상태 조회 API 추가"
```

### Codex에게 커밋 메시지 생성 요청하기

변경 내용이 많을 때 Codex에게 커밋 메시지를 초안해달라고 요청할 수 있다.

```
> git diff의 내용을 바탕으로 Conventional Commits 형식의 커밋 메시지를 작성해줘
```

### 머지 충돌 해소

```bash
git merge main
# 충돌 발생
codex
```

```
> 현재 머지 충돌이 있어. src/order/OrderService.java와 src/order/dto/OrderResponse.java에서
  충돌이 발생했고, main 브랜치의 변경사항을 우선해서 해소해줘
```

## 2. 기능 구현

### 새 API 엔드포인트 추가

```
> GET /api/orders/{orderId}/timeline 엔드포인트를 추가해줘.
  주문 ID를 받아서 해당 주문의 상태 변경 이력을 시간 순으로 반환해야 해.
  OrderTimeline 도메인 엔티티, OrderTimelineRepository, OrderTimelineService, 
  OrderTimelineController를 만들고, 단위 테스트도 포함해줘.
```

Codex가 여러 파일에 걸친 변경을 제안한다. 각 파일을 검토하며 승인하거나 수정 방향을 추가로 입력한다.

### 타입 시스템 강화

```
> src/payment/ 디렉터리의 모든 Java 파일에서 String 타입으로 선언된 금액 필드를
  BigDecimal로 변경해줘. 영향받는 테스트도 함께 수정하고, 컴파일 오류가 없는지 확인해줘.
```

## 3. 리팩토링

### 큰 클래스 분리

```
> OrderService.java가 800줄이 넘어서 분리가 필요해.
  책임을 분석해서 적절한 단위로 분리해줘.
  기존 테스트가 모두 통과해야 하고, 공개 인터페이스는 그대로 유지해야 해.
```

에이전트가 분리 계획을 먼저 설명한다. 계획을 검토하고 승인하면 실제 코드를 변경한다.

### N+1 쿼리 제거

```
> OrderRepository에서 N+1 쿼리가 발생하는 부분을 찾아서 fetch join으로 수정해줘.
  수정 전후 쿼리 수를 비교하는 테스트를 작성해줘.
```

## 4. 버그 수정

### 재현 단계 제공하기

버그 수정에서 가장 중요한 것은 재현 단계를 정확히 전달하는 것이다.

```
> 다음 버그를 수정해줘:
  
  증상: 주문 취소 후 재고가 복원되지 않음
  재현:
  1. 재고 10개인 상품 생성
  2. 주문 생성 (재고 3개 차감 → 잔여 7개)
  3. 주문 취소
  4. 재고 확인 → 여전히 7개 (기대값: 10개)
  
  관련 클래스: OrderService.cancelOrder(), InventoryService.restoreStock()
  에러 로그: null
  
  원인을 분석하고 수정한 뒤 회귀 테스트를 추가해줘.
```

### 로그와 함께 디버깅

```
> 다음 스택 트레이스를 분석해서 원인과 수정 방법을 설명해줘:

  java.lang.NullPointerException: Cannot invoke "String.length()" 
    because "com.wisehero.order.dto.OrderRequest.productCode" is null
    at com.wisehero.order.OrderService.validateOrder(OrderService.java:142)
    at com.wisehero.order.OrderService.createOrder(OrderService.java:87)
```

## 5. 코드 리뷰 보조

### PR 전 자가 검토

```
> git diff main...HEAD의 변경사항을 리뷰해줘.
  다음 항목을 중점으로 확인해줘:
  - 보안 취약점 (SQL 인젝션, 입력값 검증 누락)
  - 트랜잭션 경계 오류
  - 예외 처리 누락
  - 성능 문제 (N+1, 불필요한 DB 조회)
```

### 리뷰 코멘트 반영

```
> PR 리뷰에서 다음 코멘트를 받았어. 반영해줘:
  
  "OrderService.createOrder(): 동시 주문 시 재고가 음수가 될 수 있습니다.
  낙관적 락(OptimisticLock) 또는 SELECT FOR UPDATE를 적용해주세요."
```

## 7. 컨텍스트 관리

### 긴 세션에서 컨텍스트 유지

Codex 세션이 길어지면 초기 컨텍스트가 희석될 수 있다. 작업 중간에 핵심 제약조건을 상기시킨다.

```
> 지금까지 작업한 내용을 바탕으로 진행하되, AGENTS.md의 "절대 수정 금지" 파일 목록을
  다시 한번 확인하고 작업해줘.
```

### 새 세션 시작 시

복잡한 작업은 새 세션에서 전체 맥락을 다시 제공하는 것이 낫다.

```
> 컨텍스트를 알려줄게:
  - Java 21 + Spring Boot 3.2 프로젝트
  - PostgreSQL 기반 전자상거래 백엔드
  - AGENTS.md가 프로젝트 루트에 있음
  
  지금 할 작업은: [작업 설명]
```

## 8. 핵심 정리

- 항상 피처 브랜치에서 작업하고 변경 후 `git diff`로 검토한다.
- 버그 수정 시 재현 단계와 관련 클래스를 함께 제공한다.
- 큰 리팩토링은 계획 설명 후 단계별로 진행한다.
- PR 전에 Codex에게 보안, 트랜잭션, 성능 관점의 리뷰를 요청한다.
- 긴 세션에서는 핵심 제약조건을 중간에 상기시킨다.
