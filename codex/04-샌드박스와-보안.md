## 들어가며

Codex CLI가 다른 AI 코딩 에이전트와 구별되는 가장 큰 특징은 **OS 커널 수준의 샌드박싱**이다. Claude Code는 애플리케이션 레벨 훅으로 위험한 명령을 차단하지만, Codex는 운영체제가 직접 프로세스의 파일시스템 접근과 시스템 콜을 제한한다. 이 차이는 full-auto 모드에서 특히 중요하다.

---

## 1. 샌드박스의 목적

에이전트가 셸 명령을 자동으로 실행할 때 두 가지 위험이 있다.

1. **실수**: 의도치 않게 중요한 파일을 삭제하거나 시스템 설정을 변경하는 경우
2. **프롬프트 인젝션**: 악성 코드나 댓글이 에이전트를 조종해 의도치 않은 명령을 실행하는 경우

샌드박스는 에이전트가 실행하는 프로세스를 격리하여, 지정된 작업 디렉터리 외부에 접근하거나 네트워크를 사용하지 못하도록 OS 레벨에서 강제한다.

---

## 2. macOS: Seatbelt

macOS에서 Codex는 Apple의 **Seatbelt** 프레임워크를 사용한다. `sandbox-exec` 유틸리티가 동적으로 생성된 SBPL(Sandbox Profile Language) 정책을 적용한다.

**허용 범위**:
- 프로젝트 디렉터리(워크스페이스) 읽기/쓰기
- 임시 디렉터리(`/tmp`) 읽기/쓰기
- 일부 시스템 바이너리 실행 (`git`, `node`, `python` 등)

**차단 범위**:
- 워크스페이스 외부 파일시스템 쓰기
- 외부 네트워크 접속 (기본값)
- 시스템 환경 설정 변경

Seatbelt는 커널 레벨에서 동작하므로 에이전트가 아무리 영리하더라도 정책을 우회할 수 없다.

---

## 3. Linux: Bubblewrap + Landlock + seccomp

Linux에서는 세 가지 기술을 조합하여 샌드박스를 구성한다.

**Bubblewrap(bwrap)**

제한된 파일시스템 뷰를 구성한다. 프로젝트 디렉터리와 최소한의 시스템 경로만 마운트하여, 나머지 파일시스템에는 접근 자체가 불가능하다.

```
/ (read-only 바인드)
├── /tmp (tmpfs)
└── /workspace (read-write 바인드 — 프로젝트 디렉터리)
```

**Landlock**

Linux 5.13 이상의 커널에서 사용 가능한 LSM(Linux Security Module). 프로세스가 접근할 수 있는 파일 경로를 커널에서 직접 제한한다.

**seccomp**

시스템 콜 필터링. 에이전트가 실행하는 프로세스가 허용된 시스템 콜만 사용하도록 제한한다.

**네트워크 격리**

기본적으로 네트워크가 완전히 차단된다. 에이전트가 패키지를 설치하거나 API를 호출하려면 워크플로우 설계 단계에서 네트워크 허용 정책을 명시해야 한다.

---

## 4. 플랫폼별 비교

| 항목 | macOS | Linux |
|------|-------|-------|
| 핵심 기술 | Seatbelt (sandbox-exec) | Bubblewrap + Landlock + seccomp |
| 커널 요구사항 | macOS 내장 | Linux 5.13+ |
| 네트워크 격리 | 커스텀 정책 가능 | 기본 완전 차단 |
| 별도 설치 필요 | 없음 | 없음 (커널 지원 확인 필요) |
| 컨테이너 환경 | 제한 없음 | 호스트 커널 설정에 의존 |

---

## 5. Docker/컨테이너 환경 주의사항

컨테이너 안에서 Codex를 실행하면 Landlock/seccomp 지원 여부가 호스트 커널에 달려 있다. 일부 환경에서는 권한 부족으로 샌드박스가 작동하지 않을 수 있다.

**증상**: `codex exec` 실행 시 `bwrap: setting up newroot failed` 또는 `landlock_create_ruleset: Operation not permitted` 오류.

**임시 해결 방법**:

```bash
docker run --security-opt apparmor=unconfined \
           --security-opt seccomp=unconfined \
           your-image codex exec "작업"
```

**권장 방법**: 컨테이너 대신 GitHub Actions의 `ubuntu-latest` 러너를 사용한다. 해당 환경은 Landlock을 지원한다.

## 6. 샌드박스 수준과 승인 정책의 관계

샌드박스 수준(`sandbox_mode`)과 승인 정책(`approval_policy`)은 독립적으로 동작하지만 상호 보완한다.

- **`approval_policy`**: 에이전트가 사용자에게 확인을 요청하는 시점을 결정
- **`sandbox_mode`**: 에이전트 프로세스가 물리적으로 접근할 수 있는 범위를 결정

### sandbox_mode 옵션

| 값 | 설명 |
|----|------|
| `read-only` | 파일시스템 읽기만 허용. 쓰기·셸 명령 차단 |
| `workspace-write` | 작업 디렉터리 읽기/쓰기 허용. 외부 접근 차단 |
| `danger-full-access` | 제한 없음. 신중하게 사용 |

```
--full-auto ~= on-request + workspace-write
untrusted + read-only = 승인 중심의 안전한 읽기 전용 모드
```

`--full-auto`를 사용하더라도 샌드박스가 활성화되어 있으면 에이전트는 보통 작업 디렉터리 바깥으로 자유롭게 쓰지 못한다. 다만 정확한 네트워크 허용 범위와 플랫폼별 제약은 실행 환경 설정에 따라 달라질 수 있으므로, 보안 요구사항이 높다면 `sandbox_mode`와 네트워크 정책을 함께 확인해야 한다.

## 7. 실전 보안 체크리스트

**자동 실행 모드 사용 전**

- [ ] git 저장소가 초기화되어 있는가?
- [ ] 최근 커밋이 있어서 `git checkout`으로 되돌릴 수 있는가?
- [ ] `.env`, 인증 파일 등 민감 데이터가 `.gitignore`에 포함되어 있는가?
- [ ] AGENTS.md에 변경 금지 파일/디렉터리가 명시되어 있는가?

**CI/CD 파이프라인에 추가 시**

- [ ] `OPENAI_API_KEY`가 GitHub Secrets 등 안전한 저장소에 있는가?
- [ ] 파이프라인이 읽기 전용 브랜치가 아닌 임시 브랜치에서 실행되는가?
- [ ] 에이전트가 외부 네트워크에 접근해야 한다면 명시적으로 허용했는가?

---

## 8. 핵심 정리

- macOS는 Seatbelt, Linux는 Bubblewrap + Landlock + seccomp로 OS 커널 수준 격리를 구현한다.
- 샌드박스는 에이전트가 프로젝트 외부에 접근하는 것을 물리적으로 차단한다.
- `--full-auto`는 샌드박스와 승인 정책의 조합 프리셋이지, 무제한 권한 모드가 아니다.
- Docker 환경에서는 호스트 커널 설정에 따라 샌드박스가 작동하지 않을 수 있다.
- 어떤 모드를 사용하든 git 저장소를 유지하면 실수한 변경을 되돌릴 수 있다.
